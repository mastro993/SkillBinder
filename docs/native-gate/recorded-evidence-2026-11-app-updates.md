# Recorded evidence, November 2026: app updates

On 2026-11-21, a macOS ARM64 MCP session verified app updates in place (issue #171, slice S3) with the debug native-test build. The synthetic world from `cargo run -p xtask -- fixture` supplied the update site (`--update-dir <world>/app-updates`, Stable offering 0.2.0 with an archive under `downloads/`, payload `Executable`), and the app ran as 0.1.0 from a fixture bundle in the isolated Applications folder (`--app-bundle <data>/fixture-applications/SkillBinder.app`).

- **Ready notice (AC3.4).** After onboarding (agents kept, import skipped), the launch check downloaded and staged the archive: `.skillbinder-update-0.2.0.app` sat beside `SkillBinder.app` with the archive as its executable, and `<data>/updates/0.2.0/` was gone. The notice at the bottom-right read "SkillBinder 0.2.0 is ready" over "Restart now, or it installs when you quit.", with Dismiss and the primary Restart. Settings › Updates read "SkillBinder 0.2.0 is ready." with Restart and What's new.
- **Restart while Sync runs (AC3.4).** With the fixture remote connected and then redirected through the fixture home's `.gitconfig` to a local socket that accepts and never answers, Refresh held Sync. The notice's Restart turned disabled and its tooltip read "Available when Sync finishes"; once the socket closed and Sync ended, Restart was enabled again without reopening the notice.
- **Dismiss (AC3.4).** Dismiss took the notice down, and it did not return on moving to Settings, which still offered Restart.
- **Restart.** Settings' Restart quit the app. The log recorded "Installed SkillBinder 0.2.0."; `SkillBinder.app` held the 0.2.0 archive and `.skillbinder-old-0.1.0.app` the old one. `open -n` then failed, as expected for a fixture bundle that is not an app, and the desktop logged "Could not open SkillBinder again".
- **Next launch.** Relaunched with `--app-version 0.2.0`, the folder held only `SkillBinder.app`, and the change toast read "Updated to SkillBinder 0.2.0" with Release notes. No notice showed, since nothing newer was offered.

These are native interaction checks with a fixture payload. The packaged checks AC3.5 to AC3.7 (a notarized older build updating from `/Applications` with no Gatekeeper prompt, Dismiss then Quit, a non-admin account in `~/Applications`, and a bundle signed by another team) need two notarized releases and have not been run. Disk-image staging is covered by a macOS domain test that mounts a real image and sees `codesign` refuse its unsigned bundle.

## Windows installer and updates (#172, slice S4)

On 2026-11-21, on macOS, the Windows update logic was verified by domain tests that run on every platform (AC4.2): `location` reports NotInstalled for an executable without `unins000.exe` beside it and SetUp with it, the silent command line always carries `/WAITPID=<pid>` and carries `/RELAUNCH=1` only after Restart, a staged setup program waits in `<data>/updates/` across launches, a quit with `QuitCause::SessionEnd` starts nothing and keeps the update ready, and a setup program that does not start reopens the app after Restart. The packaged checks AC4.1 and AC4.3 (checklist item 13: no UAC prompt, the Start menu entry and the uninstaller, data kept on uninstall, Restart, Dismiss then Quit) need a Windows machine and two stamped setup programs, and have not been run.

## Linux AppImage and the applications menu (#173, slice S5)

On 2026-11-21, on macOS ARM64, the Linux update logic was verified by domain tests that run on every Unix (AC5.2, AC5.3): `location` reports NotInstalled without `$APPIMAGE` and NotWritable for an AppImage in a 0555 folder, and only an AppImage offers the menu; a newer AppImage stages beside the running one as `.skillbinder-update-0.2.0` with mode 0755, Restart swaps it in, keeping the old file as `.skillbinder-old-0.1.0.AppImage`, which the next launch removes; Add writes the entry, its `Exec` the quoted AppImage path, and the icon under the fixture's `~/.local/share`; and after Add or Not now a relaunch never offers again. `xtask update-manifest` keys `skillbinder-<version>-x86_64.AppImage` as `x86_64-unknown-linux-gnu`.

An MCP session with the debug native-test build and `--appimage <home>/Applications/skillbinder.AppImage` checked the dialog (checklist item 14): it opened over onboarding with the title, body, Not now, and Add; with `~/.local/share` blocked by a file, Add showed "Couldn't add SkillBinder to the applications menu." and the log recorded "Couldn't add SkillBinder to the applications menu: Not a directory (os error 20)"; once unblocked, Add closed it, wrote both files, and saved `applications_menu_added = true`, and a relaunch did not ask. On three fresh data directories, the close button, Escape, and Not now each closed it, wrote nothing, and saved `false`.

The packaged checks AC5.1 (the AppImage starts on Ubuntu 22.04 and 24.04 without `libfuse2`) and AC5.4 (an older AppImage in `~/Applications` updates through Restart, and the menu entry opens the new version) need a Linux desktop and two stamped AppImages, and have not been run. The AppImage itself is first built by `build.yml` on the pull request.
