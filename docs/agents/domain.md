# Domain documentation

## One context

SkillBinder is one bounded context with one product vocabulary. Keep domain terms consistent across engine operations, typed interfaces, UI copy, tests, and documentation. Do not create competing glossaries for individual packages.

## Sources of domain knowledge

- `fixtures/contracts/domain-contract.md` preserves the shipped behavior and acceptance cases at the captured baseline revision.
- `fixtures/contracts/ui-copy.md` and the canonical native captures preserve visible wording and interactions.
- `docs/architecture/native.md` defines package ownership and the target execution and storage model.
- `docs/native-gate.md` records the current implementation stage and verification limits.
- `README.md` identifies what this checkout can run.
- `docs/features/native.md` describes the implemented features. Add behavior documentation with new features rather than documenting an aspirational implementation as complete.

The shipped scope contains four onboarding steps, Discovery, import review, Library, presets, Sync, and Settings. Workspaces, Agents, skill updates, and onboarding's review of the library's first import extend that scope. Screens for entering or editing a skill's source, nested presets, and tag-management UI are outside it.

## Update documentation with behavior

Change the affected documents in the same change as the behavior. Update architecture documentation when ownership, state flow, or concurrency changes. Add a decision record only when a real choice and rejected alternatives need to survive the task.

Shared domain types belong in `crates/proto`; engine-owned state belongs in its feature module. Document invariants beside their owning types and use the same names in feature documentation. A discrepancy between code and the approved contract is a defect to resolve, not permission to silently change the contract.

Generate `docs/supported-agents.md` with `cargo run -p xtask -- registry`. Verify the reviewed registry and its evidence with `cargo run -p xtask -- verify`.

## Vocabulary

- An agent is a registered skill reader with documented global roots and a direct workspace skill directory, plus the further skill directories the reviewed overlay records for it, each `own`, `shared`, `compatibility`, or `unconfirmed`: `.kimi-code/skills` for Kimi Code CLI, `.claude/skills` for Cursor. Its registry directories stay first and are the ones the app shows and detection reads.
- A scan observes source candidates without changing their bytes.
- Importing a found skill copies one of its versions into the library, bringing in a skill that is already on this device. An import plan records the reviewed versions and expires after 300 seconds. Import is not install: installing will mean getting a skill into SkillBinder from its source, a separate feature that does not exist yet. Do not call an import an install.
- A version is one distinct content of a slug among the found skills. Importing a slug imports exactly one version, which the user chooses; once the slug is imported, its other versions are ignored.
- A library is the set of skill directories under `skills/<slug>/`. A skill's slug, its directory name, is its identity on every device. These directories and each skill's record sync through Git; everything else about the library, such as its presets and folders, is machine-local. A skill is in library when the library holds its slug; "in library" always describes skills, never agents. Library is the view of every library skill. A library skill is active when it is on right now: the active preset holds it for at least one of your agents, or at least one workspace holds it. A skill that only presets other than the active one hold is inactive. Library shows where each skill is active and filters by active, inactive, or having an update (ADR 0007).
- A library skill's record is the content the skill should have, as a Git tree hash, and its source when one is known. Every library skill has one, and it syncs with the skill. Importing, updating, and reinstalling a skill write its record; the user never edits a library skill.
- A library skill has drifted when its content differs from its record, such as after an edit made outside SkillBinder or a Pull of different content. Reinstalling a drifted skill restores its recorded content from the library's Git history, or else from its source; it never moves the skill to newer content. Copies in agents and workspaces, managed or not, never make a skill drift.
- A library skill's source is the Git repository it was published from, an optional pinned ref, and the skill's folder in that repository. It is learned at import from the `skills` lock entry beside the imported version, even when that version's content differs from what the lock recorded, or later from the lock entry of any found copy with exactly the library skill's content, and is kept in the skill's record. A skill imported without a lock entry, or from a source that is not a Git repository, has none and never has an update. A source pinned to a commit never has an update. Avoid "upstream" and "binding".
- A library skill has an update when its source's current content differs from its recorded content. Updating a skill replaces its library content with its source's current content; the skill keeps its slug, source, folder, and presets. Updates, like imports, remain uncommitted until Sync or Push. Update all updates every library skill that has an update.
- A preset is a named configuration of library skills for your agents. A preset holds each of its skills either for all your agents or for specific ones; a skill can be in any number of presets or in none, and of the presets only the active one makes it active. All your agents means every detected agent's global skill directory, counted once per directory, including agents detected later; a skill held for specific agents keeps exactly that list. Presets apply only to the global skill directories: workspaces have no presets. One preset is active at a time: the app starts with the Default preset active, clicking a preset activates it in place without opening a page, and every activation or deactivation for your agents edits the active preset and is saved immediately. Activating a preset, including the Default preset when the active one is deleted, blocks the app, showing its progress, until its managed copies in the global skill directories are written and removed; it cannot be cancelled (ADR 0007). Editing the active preset writes and removes them at once. New presets are empty. Library lists every library skill unless the user filters it; a preset never filters the page by itself, but which skills are active follows the active preset. Clone copies a preset's name as `Copy of <name>`, its color, icon, and skills with their agents into a new editable preset; the Default preset can be cloned too. Presets are flat; their skills, order, color, and icon are machine-local and do not sync. Every library starts with the Default preset, which stays first; the app never deletes it, renames it, changes its icon or color, or moves it. Deleting the active preset activates the Default preset, and its confirmation states the skills that switch adds and removes. On first boot the Default preset holds each imported skill for the agents whose global skill directory held it. Once per device, the first time the library holds skills after onboarding, such as after the import or Pull that fills it, the active preset also holds each library skill it did not hold for the agents whose own global skill directory holds a copy with the library's content, so the agents keep loading what they loaded. Avoid "folder" for presets.
- A folder, in the library, is a named grouping of library skills for browsing only. A skill is in at most one folder; a skill in none is unfiled. Moving a skill to a folder never moves its files. Folders are machine-local organization data and do not sync; a skill that arrives through Pull is unfiled. Choosing one narrows Library to its skills; nothing ever applies a folder. Folders are separate from presets: a skill's folder says nothing about its presets. All skills is Library without a folder chosen; it is not a folder. Elsewhere "folder" keeps its filesystem meaning, as in a workspace's project folder; say "library folder" where the two could be confused.
- A global skill directory is an agent's skill directory under the user's home folder, such as `~/.claude/skills` or `~/.agents/skills`. The scan checks the detected agents' global skill directories directly. They are not a workspace and have no collective name; in UI copy they are "your agents". Avoid "System", "Global", and "Root" for them; "root" keeps its filesystem meanings.
- A workspace is one project folder the user added on this device. Workspaces are machine-local. Its scan reads only the agent workspace skill directories at its top level, such as `<project>/.claude/skills`. Scanning never changes their bytes; activation, which runs before each scan, writes and removes the managed copies of the skills the workspace holds there. Adding a folder adds each project in it as a separate workspace: the folder itself and each direct child that have an agent skill directory, or the folder alone when none has one. Agent folders among them are left out, so a folder whose only projects are agent folders adds nothing. The folder is not remembered. A folder whose agent workspace skill directories include a global skill directory, such as the home folder, cannot be a workspace, and neither can a folder at or inside a global skill directory. Its name starts as the folder's last path component and can be renamed. A workspace's color, curated glyph, and image icon are machine-local appearance; an image is stored under application data and referenced only from there. Avoid "workspace root".
- A found skill is a skill folder that a scan found in a global skill directory or a workspace. Found skills are not stored: the next scan replaces them. A found skill is in library when the library holds its slug: once a skill is imported, the library is its source of truth, and copies in agents and workspaces are never new skills, whatever their content. Avoid "installed" for this state; install names a separate, future feature.
- A skill is active in a workspace when the workspace holds it, either for all its agents or for specific ones. A workspace's agents are the workspace skill directories it uses: the ones that existed when it was added and that a detected agent reads, including a directory the overlay names for that agent alone such as `.kimi-code/skills`, plus any the user adds for a detected agent, which is created on first activation. A directory it reads only because it is named for another agent, such as `.claude/skills` for Cursor, is never one until the user chooses it. Adding a workspace makes each library skill it already holds active there, for the directories that hold it: a copy with matching content is adopted, and one with other content is a conflict. Each workspace holds its own skills; nothing shares them between workspaces. Activating or deactivating a skill in a workspace writes or removes its managed copies there at once. A skill can be active both for your agents and in a workspace, and an agent may read it there and in a global skill directory it reads; the app warns rather than blocks, saying that the agent may load it twice, that it keeps your agents' copy and ignores the workspace's, that it loads the workspace copy and ignores your agents', or, where no source ranks the two, that it keeps one copy without saying which.
- A managed copy is a copy of a library skill in a global or workspace skill directory that SkillBinder wrote or adopted because the skill is active there. A copy whose content matches the library is adopted without writing; a copy of the slug with other content is a conflict, which the user replaces or skips; a replaced copy becomes managed. Apart from a replacement the user confirms, only managed copies are ever rewritten or removed, and files under other slugs are never touched: library changes rewrite them, deactivation and preset switches remove them, and a skill removed from the library loses them everywhere. A managed copy edited in place is never overwritten or removed without asking. Choices are saved before files are written; a directory that cannot be written shows the skill as not applied there until a retry or a later scan succeeds. Copies are machine-local and never sync. Removing a workspace leaves its copies in place, unmanaged. Avoid "presence" and "deployment".
- A detected agent is a registry agent whose global skill directory exists on this device, inside home where the scan reads it. That directory alone detects it: the other directories it reads do not. Its found skills are the found skills in that directory, in library or not; Discovery lists the skills found in its other directories under it too. Agents that share a global skill directory share their found skills. Agents is the view of active library skills by detected agent: an agent's page lists the library skills the active preset holds for its global skill directory, and found skills that are not in library are listed only in Discovery (ADR 0007). Avoid "installed agent".
- The universal agents are the detected agents whose global skill directory is `~/.agents/skills`. The app lists them together as Universal. The registry's agent named Universal is not necessarily one of them: its global skill directory is under the XDG config folder.
- Discovery is the view of every found skill across the global skill directories and all workspaces that is not in library. It lists each slug once, with its versions and every location where each was found. Discovery itself is read-only. Importing a found skill makes it active wherever it was found: in the active preset for the agents whose global skill directory held it, and in each workspace that held it, for those directories. Copies with the chosen version's content are adopted; copies of other versions are replaced once the user confirms the import review that states each replacement, and become managed. Other presets are unchanged.
- Sync and Push are explicit actions that may commit library changes. Imports remain uncommitted until those actions. Organization changes are never committed.

Expand this vocabulary only when a domain type or an accepted behavior introduces a term.
