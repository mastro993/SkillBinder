# Native menu bar

The app stays resident behind a menu bar or system tray icon once its window closes ([spec](../specs/menu-bar.md), [design](../specs/menu-bar/design.md), ADR 0020, ADR 0021; [feature](../features/native/menu-bar.md)). Slice S0 (#183) adds the resident lifecycle and a menu that opens the window and quits; S1 (#184) adds the presets, the attention item, and the `Gate`; S2 (#185) moves Update all and the user's Git operations into the client and adds the skill update group and the dot; S3 (#186) adds the app update group.

## Events

A backend never touches `App`. Its callbacks send a `TrayEvent` into an unbounded `async-channel`, which a foreground task spawned by `start_tray` awaits: an action goes to `dispatch`, where Open SkillBinder calls the `open_window` closure `apps/desktop` passed in, the attention item calls it and then the view's `review_copies`, and Quit SkillBinder calls `App::quit`; a lost Linux host marks the tray `Unavailable` and opens the window when none is open. After every click the menu is drawn again, since muda toggles a clicked check itself.

The menu is recomputed on every snapshot the tray receives and every change to the `Gate` (`observe_global`), and drawn only when it differs from the shown one.

## The blocking change

The view's `block` marks itself `busy` and starts the change through `gate::start_change`, and its strip observes the `Gate`: once the change leaves `Running`, the view settles it as any operation's result, landing the strip or closing it with the error. `take_strip` clears `change` on every path that ends the strip: the toast, the close after a refused change, and the Done pill's Review or Close. While the window is open, its `blocked()` (`working() || strip.is_some()`, where `working()` is `busy || snapshot.updating.is_some()`) equals the gate's, because the view writes `busy` to both and holds a strip exactly while the gate holds a change. Controls that the view's short work made inactive read `working()`, so they wait for an Update all too. `NativeView::new` registers the view as the `MainView`, and adopts a strip, shown at once, when the gate's change is running.

## Running work

Update all and the user's Git operations run in the client, which publishes them on the snapshot, so the window and the menu read the same state and closing the window stops neither.

- `Client::update_all` claims `updating = Some((0, total))` and clears `update_all_outcome` inside the watch's lock before it returns, so a second call refuses with a `Busy` error and one with no update does nothing. It then runs on the client's runtime: each skill through `update_skill`, publishing `(done, total)` after each, stopping at the first error, then one scan and the outcome, with `updating` back to `None`. The window's Update all awaits it to show an error; the menu with no window spawns it.
- The outcome stays until the next Update all starts or a source check, the hourly one or Check now, completes. The check after a scan leaves it, since it would follow Update all's own scan. The view copies a new outcome, or the outcome of a run it saw running, into its page's `update_outcome`, which navigation clears as before.
- `Client::synchronize`, the user's Git operation, publishes `syncing` while it runs; the background remote refresh at launch and focus does not. Restart's blockers (`RestartBlocker::of`) and the sidebar's Sync spinner read it.
- A full read of the engine knows nothing of these, so `publish_full` keeps the current `updating`, `update_all_outcome`, and `syncing`.
- `start_source_checks` runs `check_sources(UPDATE_CHECK_INTERVAL)` on a Tokio interval from an hour after launch, beside the app update checks, and refreshes the snapshot.

## Windows of one launch

`NativeView` is created per window. What the app update notice has shown this launch, `LaunchNotice`, is a GPUI global that the view writes when it is created and when it dismisses the notice or announces the update; a later window resumes it, and offers neither Move to Applications nor the Applications menu, which show in the launch's first window only. Under `native-test`, every window gets its own MCP bridge, which stops when the window closes, so the bridge sees no app while no window is open.

## Dependencies

`tray-icon` 0.26 (default features off, so no GTK) is a `cfg(not(target_os = "linux"))` dependency of `crates/ui`, and `ksni` 0.3 (`blocking`, `async-io`) a `cfg(target_os = "linux")` one; `png` and `async-channel` are plain ones. `xtask/src/graph.rs` allows them for `skillbinder-ui` only. Neither backend needs a denied standard-library API in the project's own code.
