# Native command line

The `skillbinder` command reaches the running app over a local socket and never opens the library itself ([spec](../specs/command-line.md), [design](../specs/command-line/design.md), ADR 0022; [feature](../features/native/command-line.md)). This page records how the pieces are built.

## Parts

| File | Responsibility |

| `crates/proto/src/command_line.rs` | The wire contract: `PROTOCOL` (8), `Hello`, `Greeting` (`Welcome` or `Mismatch`, decided by `Greeting::answer`), `CommandError` with `From<AppError>`, an exhaustive match on `ErrorCategory`, and `ErrorCode` with its exit code. `Endpoint::of(data, temp)` names the socket both sides use. `request.rs` holds `Request` (`Status`, `Open`, `Hold`, `Read { query }`, `Find { find }`, `Change { change, consent }`), `Query`, `Find` (`Scan`, `Search { query }`, `Check`, `History { before, limit }`: reads that ask the engine first), `Change` (a variant per changing command, names as strings, a workspace as `WorkspaceName { name, folder }`, and the Sync page's changes as `Sync { sync: SyncCommand }`), `Consent { replace, confirm }` of `Permission` (`Ask`, `Yes`, `No`), and `Answer`; `reply.rs` holds `Reply` (`Progress`, `Ask(Question)`, `Outcome(Result<Output, Failure>)`), `Failure { error, result }` for a change that partly landed, and each command's `Output`, whose rows, with `CommandError`, derive `schemars::JsonSchema` for the MCP server's output schemas; `explore.rs` holds `scan`'s `FoundRow` and `FoundVersion`, `search`'s `SearchOutput`, and `repos`' `RepositoryRow`; `updates.rs` holds `updates`' `UpdatesOutput` and `Unchecked`. `sync.rs` holds `SyncCommand` (`Run { action: SyncKind }` for `sync`, `push`, and `pull`, `SetRemote`, `RemoveRemote`, `Restore`, `Discard`, `Resolve { choices }`, `RenameDevice`), `sync status`'s `SyncStatusOutput`, and `sync history`'s `HistoryOutput`. |

## Endpoint

`Endpoint::of` derives the endpoint from the application data folder, so the command, the app, and a second launch agree without asking each other, and an isolated test root gets its own. On macOS and Linux it is `<application data>/command.sock`; when that path is longer than a Unix socket path allows (103 bytes), it is `skillbinder-<digest>.sock` in `$XDG_RUNTIME_DIR` where it is set, a per-user folder no one else can write to, or else in the temporary folder, which is per user on macOS (Linux's shared `/tmp` would let another user bind the name first); where `<digest>` is the 64-bit FNV-1a of the data folder's path. On Windows it is the named pipe `skillbinder-<digest>`; the data folder lies under the user's profile, so each user has their own.

The app holding `application.lock` binds it with `interprocess`'s `try_overwrite`, which removes a socket file a crash left behind. On Unix it then sets the file's mode to 0600 (`interprocess`'s own mode option is not supported on macOS). Windows' default named pipe security lets only the creating user, administrators, and the system write to the pipe, so no security descriptor is passed. A socket the server cannot bind is logged, and the app runs without the command.

## Exchange

Each line is one JSON object. The command sends `Hello { protocol, version }`; the app answers `Greeting::answer`'s `Welcome` or `Mismatch` and closes after a mismatch, which the command reports as exit 5, "This `skillbinder` doesn't match SkillBinder <version>." with the hint "Repair it in Settings › General." The command then sends one `Request` and reads `Reply` lines until `Reply::Outcome`.

The server counts a command as connected (`Commands::connect`) from its request until its outcome is written or it goes, and hands the request to the GPUI task through an `async_channel` with a `Peer`: a reply sender and an answer receiver, whose other ends form the server's `Session`. The request also carries its own `Connection`, which the dispatch holds until the request ends, so an app with no icon stays up while a change runs after its command went. `dispatch` answers before onboarding finishes only for requests `needs_setup` excludes, an exhaustive match so each new request must decide, and otherwise `CommandError::setup()`. `Status` reads the client's snapshot and the `Gate`: the active preset from `resolved_active`, Library's counts with no folder, search, or filter (`snapshot_query::library_counts`), the waiting copies the review list shows (`waiting_copies`), the Sync state, and the running blocking change's title, or the Update all progress.

`Read` answers from the snapshot at once. `Find` runs on a GPUI task: `Scan` calls `Client::prepare_found_import`, a fresh scan and plan, as the dialog does; `Check` calls `Client::check_now`, as Library's header does, then answers as `updates`; `Search` awaits `Client::fresh_catalog` (the catalog refreshed when over an hour old, as opening Explore does) and `Client::ask_skills_sh`, which asks skills.sh on a thread of its own (`Searches::ask`) without touching the search Explore shows. `Change` is refused while `Gate::blocked` holds, which also counts the command's own short changes (`Gate.commands`, held by `run::held` around a save, a copy answer, Retry, an Update, a Reinstall, a Git operation, and the replacements a command decided on, never while a question waits; the window mirrors it into `NativeView::working` through its `Gate` observer, so it refuses during them as during its own saves) (exit 4, naming `Gate::running()`, Update all, or a Git operation), planned against the snapshot, then run on a GPUI task. A switch, deleting the active preset, adding skills to a workspace, and turning an agent on go through `gate::block` with the window's `Activity` (`Switching`, `DeletingActive`, `Adding`, `TurningOn`): with a window open, `NativeView::block_change` shows the strip, setting the preset active at once as a click does; without one, `gate::start_change`, refused while blocked. The operation reports its result on a channel the run awaits; a refused start drops it, which the run reports as busy. An import goes through `gate::block` too, as `Importing`, after a fresh `prepare_found_import` (again with any named version the plan didn't take) and `agree`. Installs, adding or removing a repository, and Install all run on the client's runtime without holding the gate, as Explore's do; an install resolves its references after `fresh_catalog`, and `apply` returns a `Failure` with what landed when one install or an Install all's skill fails. Other changes run on the client's runtime as the window's saves do. Update all runs `Client::update_all`, which claims `AppSnapshot.updating` before it returns, so the window's header, the menu, and a second command see it at once. While the change runs, a task forwards each new `(done, total)` of `AppSnapshot.activation`, for Install all of `explore.install_all`, or for Update all of `updating`, as `Reply::Progress`.

After the change, the copies that ask (`ManagedCopy::asks`) and were not in the snapshot before it are settled by `Consent.replace`: `Yes` calls `Client::resolve_copy(Replace)` for each, `Ask` sends `Reply::Ask` per copy and replaces on a yes, and `No` leaves them; before replacing, `run::interrupted` refuses when something else started while a question waited (not the command's own landed switch, whose strip may still show). Any copy left, answered no, refused, or failed, makes the outcome `Err(Failure { error, result })` with the change's `Changed` and the copies still waiting. A deletion first previews (`Client::preview_delete` for a preset, the library revision for a folder), asks by `Consent.confirm` with the window's text, and passes the previewed revision into the change. A question the command never answers, because it went, counts as no.

On Ctrl-C the command's handler prints "Still running in SkillBinder." and exits 130. The server's next write fails, it drops the `Session`, and the request goes on: its replies go nowhere and its questions are answered no.

## Lifecycle

`--background` is the only argument a release build accepts; a native-test build accepts it beside its own. It skips opening the window and sets the macOS Accessory policy, so no Dock icon shows. A background launch that finds another app running exits 0, since the command reaches that one; any other second launch calls `open_running`, which connects, greets, sends `Open`, and waits for the app to close the connection once it has asked for the window, retrying for up to 12 seconds while the running app starts. It returns whether it sent `Open`, and `main.rs` prints `SkillBinder is already running; opened its window.` to stderr when it did, or `SkillBinder is already running.` when the app never answered or greeted with `Mismatch`. No `activate` file or polling thread remains. The MCP server's `Hold` gets no reply: the command server keeps it counted as a connected command until it closes, so an app started in the background stays up for an agent's session.

`quit_if_unseen` quits when no window is open, no command is connected, and the icon neither shows nor may still show (it is registering, or the preference to show it has not been followed yet). It runs when a command's connection closes, when the tray reaches `Unavailable` or is hidden, when the last window closes (after setting the Accessory policy), and 30 seconds after a background launch, should its command never connect. A background app quits through the same quit hook as any quit: it drains the engine, finishes a ready app update, and exits 0; only a foreground launch whose window failed to open still exits 1.

The command starts the app with `--background`, with no standard streams, in its own process group (Unix) or a new process group with no console window (Windows), so neither a pipe reading the command's output nor the terminal's Ctrl-C holds or stops it. It finds the app at `Contents/MacOS/skillbinder` beside itself in a bundle, at `..\skillbinder.exe` from Windows' `bin`, beside itself in a Cargo target folder, and on Linux at the path the app writes to `<application data>/app-path` at each launch (`$APPIMAGE`, else its executable). On Linux without `WAYLAND_DISPLAY` or `DISPLAY` it exits 5 naming the missing desktop session. It polls the endpoint every 100 ms for up to 20 seconds, and stops early when the app it started exits with an error. Its hidden `--data-dir` option points it at an isolated root, resolved to an absolute path with links followed as the native-test app resolves it, since the endpoint derives from the path, and passes the root on to a native-test app it starts.

Installing the command from Settings, packaging it beside the app, and connecting agents to its MCP server are in [Installing and packaging the command, and connecting agents](native-command-line-install.md).
