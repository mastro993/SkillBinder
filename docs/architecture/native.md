# Native architecture

The executable embeds one engine in its process. There is no daemon or network command transport. The native workspace implements every audited shipped journey: onboarding, Discovery and imports, Library and presets, Sync, and Settings. It also implements workspaces and the agents' global skill directories, which every scan reads, the Agents view of found skills by detected agent, and activation, which writes the active preset's skills into your agents' global skill directories, and each workspace's skills into its workspace skill directories, as managed copies.

## Ownership

| Package | Responsibility |
| --- | --- |
| `apps/desktop` | Native lifecycle, configuration, Tokio runtime, engine lifetime, process lock, and orderly shutdown |
| `crates/proto` | Shared IDs, typed inputs and results, immutable snapshots, and safe structured errors |
| `crates/engine` | Feature-oriented domain operations, jobs, persistence, filesystem operations, Git, and recovery |
| `crates/client` | Typed operations, cached projections, coalesced subscriptions, request generations, and stale-read rejection |
| `crates/ui` | GPUI entities for navigation, filters, selection, focus, dialogs, and native integration |
| `crates/theme` | Colors, typography, dimensions, and motion |
| `xtask` | Verification, registry documentation, fixtures, and packaging |

The UI invokes typed client operations. It never accesses SQLite, mutates filesystem content, or starts Git processes. Domain adapters remain private to feature-oriented engine modules.

## Execution and storage contract

The engine keeps storage and system adapters private within feature modules. A single worker owns the one connection to `skillbinder.db`, a bundled SQLite database accessed through Diesel's synchronous backend. Opening it sets a five-second `busy_timeout`, `journal_mode=WAL`, `synchronous=FULL`, and `foreign_keys=ON`, then applies the embedded Diesel migrations under `crates/engine/migrations/`; `crates/engine/src/schema.rs` declares the tables. A migration is never edited once a build has applied it, because Diesel skips migrations it has recorded; schema changes add a new migration, so existing databases upgrade in place. Its typed job queue serializes changes to skill directories, managed copies, the database, and the Git working tree. Outside application storage and the library, SkillBinder writes only managed copies of library skills in your agents' global skill directories and in workspaces' skill directories, as `docs/adr/0006-activation-writes-managed-copies.md` records. One scan of every registry agent's global skill directories and every workspace runs on its own thread: the worker prepares its inputs, and the scan publishes its found skills to a shared in-memory record that the client reads without waiting for the worker. Each found location records the agents that read it, the agents whose own global skill directory, the one the app shows, holds it through any link, and the workspaces whose scan reads it; the workspace list is empty for a global skill directory. The UI derives agent pages and sidebar counts from those agent and workspace identities, never from display paths. Found skills are scan observations and are never stored. A scan skips every directory whose name starts with `.skillbinder-`, the prefix of the staging directories copies are built in. Starting a scan replaces a running one, whose results are discarded. Source checks run the same way on their own thread: the worker lists the skills due, and the thread fetches each source into a bare, shallow, blobless cache under application data and records each skill's update state in memory; updates and reinstalls run on the worker with caches of their own, so a slow check never holds one up, and a check that panics still ends. Bounded previews run on the engine worker and never block the GPUI event loop.

The application stores machine-local state beneath the operating system's local application-data directory in `SkillBinder`; the database file is `skillbinder.db` there. Workspace image icons are copied into `icons/` there and referenced by their stored file name; a picked file is never referenced after the copy. The library is a Git repository whose managed paths are `skills/<slug>/` and each skill's record, `records/<slug>.toml`, which holds the Git tree id of the content the skill should have and its source when one is known, as `docs/adr/0004-only-skill-directories-sync.md` and `docs/adr/0005-skill-records-sync-beside-skills.md` record. A skill's slug, its directory name, is its identity on every device. Sync and Push commit only `skills/` and `records/`, and sparse checkout materializes only those. Everything else about the library is machine-local in the database, which also caches each skill's source, recorded tree, and drift: presets with their name, position, color, and icon, including the Default preset every library starts with, which always reads first and which the app never deletes, renames, recolors, re-icons, or moves; preset memberships, each holding its skill for all your agents, stored as a null `agents` column, or for the JSON array of registry identities it names; the active preset, a device setting the engine owns, which the library snapshot and its revision carry and which reads as the Default preset once the chosen preset no longer exists; the managed copies; library folders and filing; each skill's cached digest, file count, total bytes, and validation details; and its import time, absent for a skill that arrived through Pull. Workspaces also keep their name, position, color, glyph, and stored image file name there. Foreign keys remove a skill's memberships when the skill is dropped and unfile its skills when a folder is deleted; the managed copies have no foreign key to skills, so a removed skill's copies can still be removed. Each organization change is one database transaction; it is never committed to Git and never makes Sync report changes. There is no migration of an old database or library and no compatibility layer.

The engine reconciles the database with `skills/` when it opens and after onboarding creates the library: it inspects and adds directories the database lacks and drops skills whose directory is gone. It records the last commit whose skills the database reflects. When it opens and after every Pull or Sync, including a Sync whose push then fails, it rehashes only the slugs that `git diff --name-only` reports as changed under `skills/` or `records/` since that commit, or every slug when there was none, as in adoption; a Pull interrupted before this step catches up at the next launch. A Push only commits what the database already holds, so it advances the recorded commit without rehashing. A skill that cannot be inspected keeps its previous row and holds the recorded commit back, so the next launch retries it; reconciliation failures are logged and never fail a launch, Pull, or Sync. Otherwise the cached facts are trusted: SkillBinder owns `skills/`, and changes made there outside the app are unsupported. A rehashed skill keeps its import time, folder, and presets. Each inspected skill is saved with its record and drift: a record that cannot be read fails that skill's reconcile so it is retried, and a skill whose record is missing or invalid gets one from its current content, without a source, cached in the database and written to `records/` only by a Push or Sync whose fetched status shows nothing to pull, and a skill whose content's tree differs from its record's has drifted, Restorable when `git cat-file` finds the recorded tree among the library's objects or the record has a source, and otherwise Lost. The migration that added records forgets the recorded commit, so every skill is rehashed once.

Activation runs on the worker and, apart from a replacement the user confirms, changes only managed copies. A preset entry's targets resolve to the global skill directories of the detected agents it names, with links inside home resolved, each counted once however many agents share it: all your agents includes agents detected later, a list of agents never gains one, and an undetected agent in it holds nothing. The `managed_copies` table records, by resolved directory and slug, the manifest digest each copy had when SkillBinder wrote or adopted it, and what holds the directory back: a failed write, a conflict, a copy the user kept, an edited managed copy, or a failed removal. After an organization change commits, the worker brings in line each skill whose set of directories it changed, so a toggle, the agents menu, a preset switch, and deleting the active preset all write and remove copies; a failure is recorded on its directory and never rolls the choice back. For each directory and slug it writes a copy where there is none, creating a missing directory; adopts, without writing, a copy whose manifest digest equals the library skill's; rewrites a managed copy that still holds what it wrote; and removes an unedited managed copy of a skill no longer active there, one holding what it wrote or, unless it already asked as edited, the library's current content, where it also forgets any conflict or kept copy. It leaves everything else as it is and records why: a managed copy edited in place, or replaced by anything it never adopts, waits for the user, and where it manages no copy, a same-slug copy with other content, or a link, a file, a directory holding `.git` at any depth, or content it cannot read or safely copy, is a conflict. A copy the user kept is not asked about again, but is written or adopted once it disappears or comes to match the library. A directory that is the application data directory, inside it, or holding it never receives a copy and is never changed; an active skill there reads not applied with its own reason. A recorded directory whose path now leads elsewhere through a link is forgotten without touching any file. A copy is built and verified in a hidden staging directory, `.skillbinder-` plus six random letters and digits, created inside the target directory, then renamed into place, so an agent never reads a half-written skill; a rewrite or a confirmed replacement first moves the previous copy into that staging directory and moves it back if the new one cannot be moved in, and a removal renames the copy into a staging directory, then deletes it. An unasked rewrite or removal reads the moved copy again and, unless it holds what SkillBinder expects, moves it back untouched as an edited copy; a staging directory whose content could not be moved back is kept rather than deleted, renamed with a `kept-` infix that the sweep skips. Answering a copy that asks either replaces it with the library's content, after which the copy is managed, or removes an edited copy of a skill no longer active there; keeping a copy instead leaves it in place and SkillBinder no longer manages it. An answer for a copy whose record changed meanwhile, for a conflict or kept copy of a skill no longer active there, or in a directory inside application data or whose path now leads elsewhere, is refused as stale. Each scan start first deletes the leftover staging directories, named `.skillbinder-` plus exactly six letters or digits, in the directories it knows outside application data, then retries the pending directories: those with an issue, active skills with no copy on record or on disk, so a deleted managed copy is written again, active skills whose managed copy was recorded with other content than the library's, newly detected agents' directories, and managed copies of skills no longer active. Update after its batch, a Reinstall that succeeds, a Pull or Sync after reconciling, even partially, and the launch catch-up rewrite the managed copies whose recorded digest differs from the library skill's cached digest and remove those of skills no longer in the library; an edited copy is asked about instead. Copies are machine-local: they are never synced, committed, or journaled.

The same passes cover workspace skill directories. A workspace's agents are rows of `workspace_dirs`, and its skills rows of `workspace_skills`, NULL for all its agents or a JSON array of directories; both cascade with their workspace and library skill. Each workspace directory resolves inside its workspace folder, which bounds its link checks in place of home, and every directory inside a missing workspace's folder is left out of every pass, so nothing writes, removes, sweeps, or forgets anything there. A scan sweeps staging directories only in a directory that still resolves to itself inside its boundary. Adding a workspace saves its directories and the library skills it holds, each for exactly the directories holding it, in the transaction that saves its row, then brings those slugs in line, adopting matching copies and recording conflicts without writing. Each `managed_copies` record names who it is held for in `workspace_id`: the workspace holding the skill there, or NULL for your agents, which win when both hold it; a record of a skill no longer held keeps its holder. Removing a workspace, in one transaction, hands each of its records that another workspace or the active preset still holds to that holder, then deletes its row, and the cascade forgets its remaining records, leaving its files.

Navigation never cancels committed work. The engine retains terminal import outcomes, journals payload moves, and replays completed imports idempotently. An update or a reinstall journals two moves, the old directory out to staging and the new content in, and records no outcome. A journal also carries the records it changes, each with its previous version: finishing it writes them after the moves and before the database commit, and rolling it back restores the previous ones. Record files are staged under the application's `staging/` folder, so an interrupted write never leaves a temporary file under `records/`. Removing a record syncs `records/` before the journal that removed it is deleted, and record files over 64 KiB read as no record. Orphan cleanup only removes regular `.toml` files with a portable slug; anything else under `records/` is logged and left. Push and Sync write pending records through a hook that `Git::perform_with` runs right before its commit when the status it fetched shows nothing to pull, so each sync fetches once. The library repository and Reinstall's scratch repository are created with SHA-1 objects whatever Git's default object format, since records hold SHA-1 tree ids. A reinstall from the library's own objects checks the recorded tree out through a scratch bare repository under staging that borrows them through `objects/info/alternates`, so the library's index and working tree are never touched. Journals are rows in the database's `journals` table. The final transaction of an import saves its skills, records its outcome, and deletes its journal row, so the commit marker and the change it describes share one transaction. Recovery at open rolls an applying journal forward or finishes rolling back one that was rolling back, never rolls back a committed change, and must finish before further mutations. The last completed scan is retained until the next one completes.

The client publishes immutable projections through coalescing subscriptions. Full refresh generations reject superseded reads; scan results are read while holding the publication lock, so older results cannot replace newer ones. On creation, and when the window regains focus, the client starts a scan in the background unless one is already running. Each completed scan, including those after an import, an update, or a reinstall, makes the client learn sources from the scan's found copies and then check the sources not checked within the hour. Failed projection refreshes never turn a completed mutation into a failure. The library snapshot lists, outside its revision, each global or workspace skill directory where a library skill is active, apart from a missing workspace's, or where a skill no longer active there left an edited copy or a copy that was not removed, with how the copy stands and whether SkillBinder manages a copy there; a directory without a record yet reads as not applied. An organization change that changed those copies, an answer for a copy, a retry of the copies, and every Pull or Sync start a scan again, so agent pages show the copies as they now are. Detailed acceptance cases remain in `fixtures/contracts/domain-contract.md`.

The executable drains the engine in GPUI’s quit hook before native termination. This is necessary on macOS, where AppKit can terminate the process without returning from the application event loop. Quit shortcuts and last-window closure share this path. The drain cancels scanning and stops a Git command that is waiting on a remote, so quitting during synchronization returns at once instead of waiting for a process timeout; commands that change the local repository finish first, so quitting never leaves one half-applied. The worker closes SQLite and explicitly releases the library lock before shutdown returns. This also releases inherited references held by subprocesses; closing only the worker's descriptor would leave those references locked.

## Dependency boundary

`xtask verify` records each crate's allowed dependencies, so a crate can reach SQLite, GPUI, or the engine only where this document assigns it. The standard library is always in reach, so the workspace `clippy.toml` denies its filesystem, process, network, environment, and terminal APIs (and tokio's) everywhere except `crates/engine`, `apps/desktop`, and `xtask`, which replace it with their own. Clippy resolves names after macro expansion, so aliases, glob imports, and included files cannot hide a call.

The application depends on GPUI Kit 0.7.0. Kit re-exports the matching GPUI Pre 0.3.7 types, platform bootstrap, Base infrastructure, and styled components. Application crates import these APIs through `gpui_kit`; there is no separate component or platform dependency.

The Cargo `gpui-pre` patch selects the backend supplied by `gpui-mcp` revision `9dda8e5cb49990261e3fdaa26abe38112d30dafb`. The optional bridge selects its supported `gpui-pre` backend with default features disabled. Kit, its platform, and the bridge therefore share one GPUI type graph. The backend patch also applies to ordinary builds, while the bridge itself is present only with `native-test`. No dependency source is modified.

Kit enables `font-kit`, X11, Wayland, and runtime shaders through its platform dependency. The application asset source maps exercised component icon paths to licensed Hugeicons artwork and rejects unmapped icons. It does not fall back to a different icon catalog or bundle component fonts. The application sets the native system font explicitly and follows window appearance through the public theme API.

Kit's `open_window` installs its `Root` around the application view. Root owns keyboard traversal and the native dialog layer. The view owns `InputState` entities and subscriptions across renders; input changes use Kit's window-aware editing API. Typed dialog state remains in the view, and a single window dialog builder reads its current state on each render. Dismissal restores prior focus. Review dialogs use explicit footer actions and refuse implicit confirmation from Enter on the modal container. Escape, backdrop dismissal, close controls, and footer cancellation are disabled while a dialog operation is pending.
