# Native activation

Activation runs on the worker and, apart from a replacement the user confirms, changes only managed copies. A preset entry's targets resolve to the global skill directories of the detected agents it names, with links inside home resolved, each counted once however many agents share it: all your agents includes agents detected later, a list of agents never gains one, and an undetected agent in it holds nothing. The `managed_copies` table records, by resolved directory and slug, the manifest digest each copy had when SkillBinder wrote or adopted it, and what holds the directory back: a failed write, a conflict, a copy the user kept, an edited managed copy, or a failed removal. Organization changes and imports run as tracked jobs: `activation::progress` clears its record when the change is called and counts while the job runs, each pass adding the pairs it plans to the total, naming the pair it is on, and counting each pair it brings in line; passes in other jobs, such as the one before each scan or Retry, never touch it. After an organization change commits, the worker brings in line each skill whose set of directories it changed, so a toggle, the agents menu, a preset switch, and deleting the active preset all write and remove copies; a failure is recorded on its directory and never rolls the choice back. For each directory and slug it writes a copy where there is none, creating a missing directory; adopts, without writing, a copy whose manifest digest equals the library skill's; rewrites a managed copy that still holds what it wrote; and removes an unedited managed copy of a skill no longer active there, one holding what it wrote or, unless it already asked as edited, the library's current content, where it also forgets any conflict or kept copy. It leaves everything else as it is and records why: a managed copy edited in place, or replaced by anything it never adopts, waits for the user, and where it manages no copy, a same-slug copy with other content, or a link, a file, a directory holding `.git` at any depth, or content it cannot read or safely copy, is a conflict. A copy the user kept is not asked about again, but is written or adopted once it disappears or comes to match the library. A directory that is the application data directory, inside it, or holding it never receives a copy and is never changed; an active skill there reads not applied with its own reason. A recorded directory whose path now leads elsewhere through a link is forgotten without touching any file. A copy is built and verified in a hidden staging directory, `.skillbinder-` plus six random letters and digits, created inside the target directory, then renamed into place, so an agent never reads a half-written skill; a rewrite or a confirmed replacement first moves the previous copy into that staging directory and moves it back if the new one cannot be moved in, and a removal renames the copy into a staging directory, then deletes it. An unasked rewrite or removal reads the moved copy again and, unless it holds what SkillBinder expects, moves it back untouched as an edited copy; a staging directory whose content could not be moved back is kept rather than deleted, renamed with a `kept-` infix that the sweep skips. Answering a copy that asks either replaces it with the library's content, after which the copy is managed, or removes an edited copy of a skill no longer active there; keeping a copy instead leaves it in place and SkillBinder no longer manages it. An answer for a copy whose record changed meanwhile, for a conflict or kept copy of a skill no longer active there, or in a directory inside application data or whose path now leads elsewhere, is refused as stale. Each scan start first deletes the leftover staging directories, named `.skillbinder-` plus exactly six letters or digits, in the directories it knows outside application data, then retries the pending directories: those with an issue, active skills with no copy on record or on disk, so a deleted managed copy is written again, active skills whose managed copy was recorded with other content than the library's, newly detected agents' directories, and managed copies of skills no longer active. Update after its batch, a Reinstall that succeeds, a Pull or Sync after reconciling, even partially, and the launch catch-up rewrite the managed copies whose recorded digest differs from the library skill's cached digest and remove those of skills no longer in the library; an edited copy is asked about instead. Copies are machine-local: they are never synced or committed, and only an import journals the records of the copies it replaces.

The same passes cover workspace skill directories. A workspace's agents are rows of `workspace_dirs`, and its skills rows of `workspace_skills`, NULL for all its agents or a JSON array of directories; both cascade with their workspace and library skill. Each workspace directory resolves inside its workspace folder, which bounds its link checks in place of home, and every directory inside a missing workspace's folder is left out of every pass, so nothing writes, removes, sweeps, or forgets anything there. A scan sweeps staging directories only in a directory that still resolves to itself inside its boundary. Adding a workspace saves the directories it has that detected agents read and the library skills it holds there, each for exactly the directories holding it, in the transaction that saves its row, then brings those slugs in line, adopting matching copies and recording conflicts without writing. Each `managed_copies` record names who it is held for in `workspace_id` and `workspace_dir`: the workspace holding the skill there and the directory it holds it through, or NULL for your agents, which win when both hold it; a record no longer held whose holder's directory no longer leads to it, as after a link in the project changed, is forgotten without touching it; every pass hands a held pair's record to its current holder, and a record of a skill no longer held keeps its holder. Adding skills from the Add skill picker (`activation::adding`) is one tracked job like an organization change: it refuses the whole batch before saving anything when it is empty, a skill has no agent, or a skill is no longer in the library, then merges each skill into what its place holds and never narrows it. For your agents it adds the chosen agents to the active preset's entry, keeping All agents; for a workspace it holds the skill for all its agents or the union of the ticked directories with those it held, All agents winning, and adds each ticked directory the workspace does not use yet, each a detected agent's, to `workspace_dirs` first, so a skill held for all agents covers it. It saves in one transaction, runs one pass over every slug whose directories changed, and the client scans once afterwards. Removing a workspace, in one transaction, takes every record held for it or in a directory where it holds that skill now, hands each one the active preset or another workspace, present or missing, still holds to that holder, forgets the rest, and deletes its row, leaving its files.

An import saves where each new skill becomes active in its final transaction, with the skills: the active preset's entry for the agents whose own global skill directory held a copy that preparation found adoptable or replaceable, each workspace's entry for the directories it uses that held one, and a `managed_copies` record for each replacement the review stated, holding the digest that copy had at review and held for its preset or workspace. A preset or workspace removed meanwhile is skipped with the replacements held for it, so recovery never fails on one. After the commit the worker brings the new slugs in line: matching copies are adopted, and each replacement, recorded as a managed copy of what the user confirmed replacing, is rewritten with the imported content, or asks as edited once it holds anything else. First boot prepares the same plan from a scan of the global skill directories alone, run on the worker during onboarding's import step. The library skills your agents already have are adopted once per device by `activation::adoption`, which the worker runs after launch's catch-up, after onboarding completes, after each import, and after each Pull or Sync, and which does nothing until onboarding is complete and the library holds skills. It probes each detected agent's own global skill directory once per slug the active preset does not hold, skipping SkillBinder's storage and pairs `managed_copies` already records, saves the active preset's entries for the agents whose copy matches a fresh read of the library skill together with the `agent_copies_adopted` device setting in one transaction, and then runs a pass over those slugs, which adopts the copies.
