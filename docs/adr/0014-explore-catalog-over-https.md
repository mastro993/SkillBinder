# Explore reads a catalog SkillBinder publishes over HTTPS and searches skills.sh live

Partly superseded by ADR 0018: the HTTP client also fetches the signed app update manifests from `updates/` on the same Pages site and downloads release archives from GitHub Releases.

Until now, the library reached the network only through `git`: Sync and Push, checking sources for updates, Update, and Reinstall. Explore needs more than that. It shows skills the user does not have yet: the skills of curated creators, the ones trending this week, and search results. The curated list must change without an app release. Install counts live on skills.sh, and trending needs a history of them that no single request can give. So the catalog is published by SkillBinder itself, and the app reads it over HTTPS.

The catalog lives in SkillBinder's own repository, beside the app. `catalog/curated.toml` lists the creators and their repositories, and changes to it are ordinary pull requests; the app has no way to suggest one. A GitHub Actions job runs every night and on every push to `main` that changes `catalog/`. It lists each curated repository's skills with the rules the `skills` CLI uses to find them and reads each skill's name and description from its `SKILL.md`. It reads each skill's total installs from skills.sh, adds the day's totals to the history it published the night before, and computes the installs each skill gained over the last 7 days. The job never commits: its history travels with the published site, so `main` gains no bot commits and no nightly CI runs. It mirrors each creator's GitHub avatar. Then it publishes `v1/catalog.json`, `v1/avatars/<creator>.png`, and its history to the repository's GitHub Pages site, which serves them through a CDN. Popularity is computed only by this job, never by the app. The job holds the only GitHub token. When skills.sh changes, the job fails loudly, and the published file keeps the last counts.

The catalog file holds metadata only: for each creator an id, a name, and an avatar, and for each skill a slug, a name, a description, a creator, a repository URL, the skill's folder in it, and its installs this week. It never holds a skill's `SKILL.md` text or files. A skill's content stays under its repository's license and always comes from its source through `git`: the detail sheet's file list and `SKILL.md` text, and Install itself, fetch the skill's repository with the same hardened `git` process that checks sources for updates (ADR 0005). Repositories the user adds are listed the same way, through `git`, and never go through the HTTP client.

The engine gains one HTTP client, `ureq` 3, blocking, with rustls for TLS and no OpenSSL, in `crates/engine`, the only app crate that has it. It makes GET requests to exactly two places: the catalog's base URL, a compiled-in constant that isolated and `native-test` configurations override, and `https://skills.sh/api/search`. Each request sends `User-Agent: SkillBinder/<version>` and, for the catalog, `If-None-Match`; it sends no cookies, no identifiers, and no telemetry. Requests time out after 10 seconds, and responses are capped: 8 MB for the catalog, 256 KB for a search, and 256 KB for an avatar. HTTP requests run on one engine thread, and Explore's Git network work on at most three more, as checking for updates runs on its own. None of it runs on the worker that applies changes, and a search never waits behind a clone. The engine's `catalog` module translates the catalog file and the skills.sh search payload into the shared typed contracts; neither external shape reaches `crates/proto` or `crates/ui`.

Search shows matches from the catalog and the user's repositories at once. It also sends the query to skills.sh, after 2 characters and a pause of about 300 ms, for the skills no curated creator publishes. Those results are appended below the others, never reorder them, and are each tagged "skills.sh". A skills.sh result has no folder; it is found in its repository by the same rules when the user previews or installs it.

This partly supersedes ADR 0005, which rejected the GitHub REST API partly because it would add an HTTP dependency. That dependency is now accepted, for these requests only. The GitHub REST API stays rejected, in the app and for checking sources, for the reasons ADR 0005 gives: unauthenticated calls are limited to 60 per hour, and private repositories would need a token. This also partly supersedes ADR 0008, insofar as the sidebar gains a page again: Explore, its first row. Discovery stays retired. It listed found skills that are not in library, and those are still imported only through the Import skills dialog. Explore lists skills from the catalog, which are on no disk yet, and installs them from their source.

## Considered Options

- Fetching the catalog with `git` was rejected. Browsing must work without Git (ADR 0011), and cloning SkillBinder's repository to read one file would download far more than it, while a static file with an ETag costs one conditional request that usually returns nothing new.
- A separate catalog repository was rejected. It is one more repository to own and secure, and its only advantage, keeping the nightly history commits out of the app's history, disappears once the job keeps its history in the published site instead of committing it.
- Committing the history to the repository every night was rejected. It would add a bot commit to `main` daily, run the app's CI for nothing, and move the base under every open branch.
- Bundling the catalog in the app was rejected. Creators, skills, and counts would change only with a release, and trending would be stale from the day it shipped.
- Calling GitHub's API for stars at runtime was rejected. Unauthenticated calls are limited to 60 per hour per IP address, more would need a token (ADR 0005), and stars measure interest in a repository, not installs of a skill.
- Using skills.sh's authenticated v1 API was rejected. It needs a key; a key compiled into a desktop app is readable by anyone who has the app, and asking every user for their own key adds an account nobody asked for. The public search endpoint answers what the app and the nightly job need.
- Mirroring all of skills.sh into the catalog was rejected. Curation is the point of the catalog's sections, the file would outgrow its size cap, the nightly job would run into skills.sh's per-IP rate limits, and live search already reaches the long tail.
- Searching only the catalog and the user's repositories, without skills.sh, was rejected by the user, though it sends nothing to a third party. Skills outside the curated list would be unreachable unless the user found and added their repository by hand. Queries go to skills.sh instead, and this record says so.
- Publishing `SKILL.md` texts and skill files on the CDN was rejected. Redistributing them would have to honor each repository's license, the copy could differ from what Install fetches, and a preview read from the source shows exactly what Install will put in the library.
- An async HTTP stack on tokio's networking was rejected. The engine runs blocking work on its own threads, a few GET requests per session need no runtime, and an async stack adds a large dependency tree to build, audit, and keep patched.

## Consequences

- Privacy: search text leaves the device. Each query from 2 characters on goes to skills.sh with the User-Agent and the user's IP address, and nothing else. There is no setting to turn live search off; a user who searches nothing sends nothing. The catalog request reveals only that a copy of SkillBinder is running.
- skills.sh's search endpoint is undocumented and rate-limited per IP address, so it can change or refuse requests. The engine reads it tolerantly: unknown fields are ignored, and any failure leaves the local results in place with a quiet line that skills.sh is unavailable. The nightly job can break the same way; the published file then keeps its last counts.
- `<data>/catalog/` holds the last catalog file with its ETag and fetch time, and the creators' avatars. It is refreshed at launch and when Explore opens if it is older than an hour, by a conditional request. Offline, Explore shows the cached catalog and the repositories' last listing with one quiet line; on first use with no cache and no network, it shows "Couldn't load the catalog" and Retry.
- The catalog's schema is versioned by its path. Fields can be added to `/v1/`, and an app ignores the ones it does not know. A breaking change publishes `/v2/`; an app that finds no `/v1/` keeps its cache and says "Update SkillBinder to see the latest catalog".
- `ureq`, with rustls through its TLS feature, is a new dependency of `crates/engine`, the only app crate that has it, and of `xtask`, which is never shipped and runs the catalog job: the crate graph policy in `xtask/src/graph.rs` keeps it out of every other crate, the Clippy policy keeps `std::net` there too, and the third-party notices record both. Tests read a fixture catalog and fixture search results from a directory, so CI makes no network requests.
- The catalog job is part of SkillBinder's repository but not of the app, and it needs an owner. The repository's GitHub Pages site belongs to the catalog; any other site would share it under another path. A failed deploy keeps the previous site, history included; a lost site restarts trending from an empty history. Moving the catalog to another host changes the base URL constant, which needs an app release, unless the old host redirects.
- Browsing Explore needs no Git. Install, the detail sheet's file list and `SKILL.md` text, and the user's repositories need it, and say so with the app's Install Git action (ADR 0011).
