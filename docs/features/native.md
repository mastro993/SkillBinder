# Native feature coverage

The audited shipped baseline is revision `83d55ef789a7cf256021f6620742e0e9021a8312`. Main was fetched and the rewrite branch rebased before reconstruction; that revision remained current. The baseline exposes 29 application operations across the journeys below. The user deferred UI fidelity and polish; functional behavior remains required.

## Setup and lifecycle

Four persisted steps cover prerequisites, source boundaries, optional synchronization, and final library creation. Backward navigation is allowed; forward skipping is refused. Git 2.39 or newer and writable storage are required. Library initialization stages metadata and a repository before atomically publishing the directory. Completion is idempotent.

The executable owns the Tokio runtime and process lock. A second launch requests activation of the existing native window through an app-owned local marker. The Linux window uses the `skillbinder` application ID matching its desktop entry; Wayland compositors retain control over whether an activation request raises the window or requests attention. Shutdown cancels discovery and drains durable operations before flushing logs.

## Workspaces

A workspace is a project folder the user adds, which SkillBinder scans for skills. Its canonical path is its identity; its name starts as the folder's last path component, can be renamed, and need not be unique. Workspaces are machine-local SQLite state outside Git. The agents' global skill directories under home, such as `~/.claude/skills`, are not a workspace; the Agents section shows their skills. SkillBinder never writes into a global skill directory or a workspace; adding skills to them is planned with a later redesign.

The Workspaces section's add button opens native directory selection, which issues the same single-use grant valid for 300 seconds. The picked folder adds its projects as workspaces at once: the folder itself when it has an agent workspace skill directory, such as `.claude/skills`, and each direct child that has one, in name order. Hidden and linked children are skipped, so picking `~/Projects` adds `~/Projects/api` and `~/Projects/web` but not a project's own `.agents` folder. A folder where nothing has an agent skill directory is added alone as an empty workspace. The parent folder is not remembered: picking it again adds only the projects not yet added, and a folder whose projects are all added is refused, naming the existing workspace when the folder itself is the only one, and otherwise with "Every project in <folder> is already added." Nested workspaces are allowed. A scan then covers the new workspaces. Removing a workspace forgets it, then scans again; files in the folder are never touched.

An agent folder cannot be a workspace. An agent folder is one whose agent workspace skill directories, those of any registry agent such as `.claude/skills` or `skills`, include a global skill directory the scan reads, as its expanded template or its resolved path, or one at or inside such a directory, such as `~/.claude/skills` itself or a skill folder in it. Like the scan, this counts only directories under home: one that lies outside home, or links out of it, is skipped by the scan and makes no folder an agent folder. A path spelled through a link to home, such as `$HOME` when home itself is reached through a link, counts as inside home, both for environment-variable roots and for link targets. A directory that does not exist yet counts where it would be created, following links as far as they exist, including a link whose target is missing, so `~/agent-data` is an agent folder when `~/.claude` links to it or when `~/.claude/skills` links to `~/agent-data/skills`. A folder's own skill directories are compared with links resolved too, so a project whose `.claude/skills` links to `~/.claude/skills` is an agent folder. The home folder is one through `~/.claude/skills`, and so is a folder that is not hidden, such as `~/.config/opencode` through `skills`. Picking an agent folder skips it but still adds its qualifying direct children. An agent folder among the children of a picked folder is skipped silently, and it still counts as a project, so a folder whose only projects are agent folders, such as `/Users` holding only the home folder, is not added as an empty workspace. When nothing is added, the pick is refused with "Your home folder's skills are shown under Agents." if the home folder was one of the skipped agent folders, and otherwise with "This folder's skills are shown under Agents." A stored workspace that is an agent folder is forgotten when the engine opens on launch; its files are untouched, and the log records it.

A workspace's page shows its folder path, and notes when the folder is missing. The skills a workspace holds are listed in Discovery.

## Scanning

One scan covers every registry agent's global skill directories and every workspace whose folder exists. It walks each global skill directory with the global limits: depth 8 and 5,000 entries per walk. For a workspace it walks only the agent workspace skill directories at the top of its folder, such as `<workspace>/.claude/skills` or `<workspace>/.agents/skills`, with the workspace limits: depth 12, 200,000 entries per walk, the workspace exclusion names, and the mount-boundary stop on Unix. A `SKILL.md` outside a known skill directory, including one in a deeper project's skill directory, is ignored. A skill folder found through several agent directories or workspaces is listed once per physical folder. Each found location records the workspaces whose scan reads it; the list is empty for a global skill directory.

The app refreshes only on launch and when its window regains focus after losing it. A refresh starts a scan, then refreshes the Git status when a remote is connected. Adding or removing a workspace, applying an install, and Rescan in Discovery's header also start a scan. Starting a scan replaces a running one, whose results are discarded, so a scan always covers the workspaces as they were when it started. Found skills are scan observations kept in engine memory, not in the database; the last completed scan stays visible while the next one runs, and counts update when it completes. There is no filesystem watcher and no cancellation. A workspace whose folder is missing stays listed with a warning glyph and is skipped.

## Agent pages

A detected agent's page shows its global skill directory, a "Shared with" line naming, as the Agents section names them, the other detected agents that read the same directory, including through a link inside home such as `~/.claude/skills` pointing to `~/.agents/skills`, and its found skills. Universal's page shows `~/.agents/skills`, a "Used by" line naming the detected universal agents, and the found skills of that directory. The found skills are counted as "1 found skill" or "<n> found skills". They are every skill folder the last scan found in the shown directory, directly or through a link, sorted by slug, marked Installed when their content matches a library skill and otherwise Not installed, Invalid, or Blocked from their validation. Workspace copies are not included, and neither are copies in an agent's further registry roots, such as OpenClaw's `~/.clawdbot/skills` beside its `~/.openclaw/skills`; Discovery still lists them. The page is read-only. An Installed row has Show in Library, which opens Library with every skill; other rows have no action. Folders without a `SKILL.md` and folders whose inspection failed are not listed, and found skills are known only after the first scan since launch.

## Discovery

The retained registry covers 79 agents. Templates expand home and environment defaults. Shared physical skill directories list every reader label. Discovery lists the skills the scan found in the agents' global skill directories and every workspace, not arbitrary document folders. Global skill directories and workspaces are walked with separate depth, entry, exclusion, and mount policies. Links are limited to 16 hops, including links inside discovery locations before physical-path deduplication. Source aliases retain their original path for install revalidation. Discovery is read-only and never writes into a global skill directory or a workspace.

Each discovered skill appears once per slug and content digest, listing every location where those bytes were found, such as `~/.claude/skills/review` and `~/Documents/workspace/.agents/skills/review`, with the readers of each location. The same slug with different content stays a separate entry. Content alone does not merge entries, because the slug becomes the library skill's identity. Copies also merge only when their validation results match: the digest leaves out entries that inspection blocks or excludes, so a copy with an external link stays a separate, blocked entry instead of hiding an installable copy.

Discovery lists the found skills that are not installed, under the lead "Skills found in your agents and workspaces that are not installed." Its status line shows "Scanning…" while a scan runs and counts found entries, not their locations, as "N found · M already installed". A found skill is installed when its content matches the inspected current payload bytes of a library skill rather than cached metadata digests. An entry's identity follows its content, so the entries chosen for install stay chosen across scans that still find them. Failed findings cannot be installed. The UI pages by 50 candidates and supports page selection and invalid-metadata acknowledgement. Distinct content sharing a slug remains visible. Unreadable or blocked managed payloads cannot hide a discovered source. A failed worker launch becomes a failed scan and permits retry. Detailed scan exclusions and failures belong in redacted logs.

## Reviewed installs

Preparation re-inspects opaque selected candidates and creates a durable immutable install plan valid for 300 seconds. An entry with several locations installs from the first location the scan found; its content and validation match the others, and review shows that location as the source. Blocked payloads are refused; invalid metadata requires acknowledgement. The Review install dialog shows source, destination, validation, size, and duplicate handling, with Back and Install actions. Pending application prevents dismissal. The result, "Install finished: N copied, N already installed, N name conflicts", survives navigation and restart until dismissed.

Application rechecks source identity, source paths, manifests, library revision, and the actual managed catalog. Every source is staged before the first managed move. Internal links become regular entries. Sources remain byte-identical. Content identical to a library skill is reported as already installed and copies nothing; distinct content sharing a slug creates a separate managed copy. Applying a completed plan returns the stored result, including after restart or plan expiry.

Payload policy preserves the captured limits, portable names, Unicode case collisions, YAML restrictions, plugin exclusions, executable flags, and explicit directories. The canonical digest is `sha256:` followed by the schema-1 manifest hash.

## Library and organization

Library supports text search, preset pages opened from the sidebar, preset creation and rename, and revision-checked deletion previews. A preset is a named set of library skills; a skill can be in any number of presets. A preset page lists the skills it holds. Deleting a preset leaves its skills in the library and in their other presets. Presets keep a user-defined order, an optional color, one of a fixed eight-color palette or any custom color, and an icon from a curated set of 40. New presets are appended last without a color and with the folder icon. Reordering requires every current preset exactly once, and positions are renumbered densely after each organization change. Names are trimmed and unique under NFKC plus full Unicode case folding. Portable tags remain stored and validated without tag-management UI. Adding skills to a preset and removing them has no UI for now: the engine supports both, each idempotent, and Library has no selection.

The page starts with a search field with a search glyph and a clear button and the number of listed skills, then, at the trailing edge, a GPUI Kit segmented control with List and Grid segments. Search matches the slug, display name, or description, ignoring case, and an empty result shows "No skills match '<query>'". Skills are listed alphabetically by their shown name, the display name or else the slug, ignoring case. The chosen view is a machine-local preference, List by default, and survives restart. List shows one row per skill: the name, one description line, its dates, and the skill's presence. Grid shows cards with the name, two description lines, dates, and presence, in as many columns at least 260 points wide as fit. Rows and cards have no action: skill details are deferred. Dates read "Installed 3 days ago · Modified 2 hours ago" in the largest whole unit, or "just now" under a minute, and each one's tooltip shows the exact local date and time. Installed is the time recorded in the skill's portable `importedAt` at install; skills installed before it was recorded show only Modified. Modified is when the newest file of the skill's managed copy last changed on this device, read from the file system each time the library is projected, so on another device it reflects that device's checkout.

Presence shows one chip per Agents row whose global skill directory held a copy with the skill's content at the last scan: Universal for the universal agents together, even when only one of them is detected, then each other detected agent in Agents section order. A copy counts when the scan found it in the global skill directory of one of the row's agents, directly or through a link, as on the agent page and in the sidebar counts. Workspace copies are not part of presence, so there are no workspace chips. Each chip is a small secondary tag holding the agent's avatar and its Agents section name. The avatar shows the agent's full-color logo on white when one is bundled, otherwise its monochrome logo or the square terminal glyph in the text color; Universal uses the layers glyph. A chip's tooltip shows the global skill directory, and Universal's adds a line "Used by <names>" naming its agents. Clicking a chip opens that agent's page or Universal's. Three chips show before the rest collapse into a "+N" chip whose tooltip names them. Before the first scan presence reads "Not scanned yet", and a library skill no detected agent holds reads "Not in any agent".

Bounded file previews, used by the shared-name dialog, list at most 5,000 entries and depth 32; text is limited to 128 KiB. Binary and oversized files remain listed with an explanation. Relative-path and canonical containment checks reject traversal and escaping links.

Shared-slug resolution previews the copies, chooses one winner, validates the expected identities and revision, and moves losers to app-local backups outside the Git repository. Resolution never writes into a global skill directory or a workspace.

## Synchronization

Connect, Refresh, Pull, Push, Sync, and Disconnect use a verified absolute Git executable with a 30-second process timeout. Status refreshes with the app, on launch and when the window regains focus, and with Refresh on the Sync page. User credential helpers remain available; prompts are disabled and credentials are not stored in application settings. App-owned Git attributes disable filters, line-ending conversion, ident expansion, and working-tree encoding so portable payload bytes survive synchronization. Remote URLs and branches are validated. The selected remote is reconciled with `origin`.

Refresh fetches without committing or merging. Pull is fast-forward only. Divergence and dirty managed files behind the remote require manual reconciliation. A newly initialized, empty, unborn library can adopt a populated remote through explicit Pull or Sync; a durable adoption journal protects its initial metadata.

Installs and organization changes remain uncommitted until explicit Push or Sync. Commits cover only `.skillbinder.json` and `skills/`, including managed files matched by ignore rules. Unrelated staged files block synchronization without changing the index. Sparse checkout prevents unrelated remote paths from materializing. Existing unrelated local files are preserved.

## Durability and diagnostics

One worker owns bundled SQLite and serializes library and Git mutations. Scans run on their own threads; the worker only prepares their inputs. Journals persist applying or rolling-back direction, next-move intent, and expected physical identity and digest. Recovery completes or reverses interrupted moves before allowing further mutations. Unknown states retain their journal and block writes. Recovery refuses externally changed portable metadata before moving payloads or replacing metadata. A committed database transaction is never rolled back through filesystem-only recovery.

Portable schema 3 stores presets, tags, and skills as maps keyed by identity, and each skill lists the presets that hold it in sorted `presetIds`; reads refuse a list that is unsorted or repeats a preset. Preset order, color, and icon are portable fields; a palette color is stored by name and a custom color as `#rrggbb`, and reads refuse any other value, so they sync with the library; reads sort presets by position, then name, so duplicate positions from separate edits never block loading. Reads accept schema 2, whose `folders` and single `folderId` become presets and a one-element `presetIds`; the next library write saves schema 3, and Sync or Push commits it. A write that fails and rolls back restores the metadata file byte for byte, so it leaves schema 2 in place. App versions that predate presets refuse schema 3 rather than drop memberships (ADR 0002). Machine-local metadata, plans, outcomes, workspaces, preferences, logs, staging, journals, and backups live in platform-local storage. No old database is migrated.

Logs use a bounded queue, 5 MiB rotation, at most five files, and 14-day retention. Home paths and common credential formats are redacted. Settings reveals only the engine-owned log directory. Safe errors include category, recovery action, retryability, and diagnostic identity.

## Acceptance evidence
