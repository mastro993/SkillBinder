# Native feature coverage

The audited shipped baseline is revision `83d55ef789a7cf256021f6620742e0e9021a8312`. Main was fetched and the rewrite branch rebased before reconstruction; that revision remained current. The baseline exposes 29 application operations across the journeys below. The user deferred UI fidelity and polish; functional behavior remains required.

## Setup and lifecycle

Four persisted steps cover prerequisites, source boundaries, optional synchronization, and final library creation. Backward navigation is allowed; forward skipping is refused. Git 2.39 or newer and writable storage are required. Library initialization stages metadata and a repository before atomically publishing the directory. Completion is idempotent.

The executable owns the Tokio runtime and process lock. A second launch requests activation of the existing native window through an app-owned local marker. The Linux window uses the `skillbinder` application ID matching its desktop entry; Wayland compositors retain control over whether an activation request raises the window or requests attention. Shutdown cancels discovery and drains durable operations before flushing logs.

## Global, workspaces, and deployments

Global is the set of global agent skill locations under home; the app labels it System. It is always present and cannot be renamed or removed. A workspace is a folder the user adds. Its canonical path is its identity; its name starts as the folder's last path component, can be renamed, and need not be unique. Global and workspaces are deployment targets. Each target has target agents. Every scan adds an agent to them the first time it finds that agent's skill directory at the top of the target, such as a newly installed agent or one whose directory a registry update moved to a folder that exists. The target remembers which agents its scans have found, so an agent the user removes stays removed while its directory remains. Databases from before this was recorded count every agent the target had then as already found. A deployment records that a target holds a copy of a library skill: the skill, the manifest digest the copy had when recorded, and every path where the copy was found. Workspaces, target agents, and deployments are machine-local SQLite state outside Git. They replaced the former workspace-search roots, which were dropped without migration.

The Workspaces section's add button opens native directory selection, which issues the same single-use grant valid for 300 seconds. An exact duplicate canonical path is refused with a message naming the existing workspace; nested workspaces are allowed. Once a folder is picked, a skeleton row appears at the end of the workspace list and a modal shows the scan's progress as the number of folders checked. Only one workspace is added at a time. Cancel, Escape, or the backdrop discards the scan and saves nothing; if the scan was saved just before Cancel arrived, the modal shows its summary instead. A failed scan saves nothing and shows a safe error with Close. A finished scan saves the workspace and its deployments in one transaction and shows a summary, "N in library, M importable", that lists each importable skill with an "importable" label, and Done. The summary only labels importable skills; they are imported from the target page.

A workspace scan walks the whole folder with the workspace traversal limits: depth 12, 200,000 entries per walk, the workspace exclusion names, the mount-boundary stop on Unix, and 16 link hops. In every directory it looks for each registry agent's workspace skill directory, such as `.claude/skills` or `.agents/skills`, and walks those for skills. A `SKILL.md` outside a known skill directory is ignored. Folders of other registered workspaces inside the workspace are skipped, so the deepest workspace holds their skills; adding a nested workspace immediately takes those copies away from the workspaces that contain it, and removing it lets their next rescan find them again. A Global scan walks the registry's global locations with the global limits. A skill whose manifest digest matches a library skill becomes a deployment; any other skill is importable. A copy found in several agent directories is one deployment with several paths, and identical importable copies with the same slug and validation result are one importable skill with several paths.

Each target is rescanned on launch, one at a time, and whenever its row is clicked. A rescan runs in the background with a spinner on the row and no modal, and replaces the target's recorded deployments with the ones it finds. A recorded copy stays recorded with its digest when its bytes changed or when it is gone, and the rescan records which copies changed or went missing; see Drift below. When it saves, it drops copies inside workspaces that are nested in the target at that moment, and a rescan requested while one runs makes it run once more. A rescan that overlapped a deployment write or a target agent change saves nothing and runs again. There is no filesystem watcher. A workspace whose folder is missing stays listed with a warning glyph; rescanning it, or a workspace whose folder cannot be read, changes nothing and keeps its last deployments. A rescan of a workspace removed meanwhile does nothing. Removing a workspace forgets it, its target agents, and its deployments; files in the folder are never touched.

## Deployment target pages

Global's page and each workspace's page show the target's location, its target agents with the skill directory each one receives, and its deployments with every recorded path. A missing workspace folder is noted and blocks adding, removing, and resolving drift until it returns.

Edit agents turns the agent list into a checklist of every registry agent: for a workspace, each with its workspace skill directory such as `.claude/skills`; for Global, each agent with a global skill directory on this device. Save agents replaces the target agents; existing copies stay where they are. A target with no target agents, such as a workspace without an agent skill directory, shows that adding skills asks which agents receive them.

Agents whose skill directories resolve to the same folder, for example through a link, share one copy. Add skills opens a dialog listing the library skills not yet deployed to the target. When the target has no agents, the dialog also lists the agents to choose, and saves them before adding. Adding copies each chosen skill into every target agent's skill directory, one directory per shared path, as `<directory>/<slug>`. Copies are ordinary files with the library payload's bytes and executable bits, never links. Each copy is staged beside its destination, verified against the library manifest, and renamed into place. A directory that already holds identical bytes is recorded without writing. One that holds anything else refuses the whole addition before any write, naming the path. Each deployment records the library digest and every path.

Remove deletes a deployment's copies at its recorded paths and forgets it; the library skill stays. Clean copies are deleted without a prompt. When a copy no longer matches the recorded digest, nothing is deleted and a confirmation lists the changed copies; Discard changes and remove deletes exactly those. A copy that changed after the confirmation opened is listed in a new confirmation instead of being deleted. Each copy is moved to a scratch sibling before it is checked, so a copy changed during removal is put back and stays recorded.

## Agent pages

An installed agent's page shows its logo and name, its global skill directory, a "Shared with" line naming the other installed agents that read the same directory, and its installed skills. The installed skills are every skill folder Global's last scan found in that directory, sorted by slug: library deployments, marked In library, Changed, or Missing from their recorded copy state, and importable skills, marked Importable, Invalid, or Blocked from their validation. Workspace copies are not included. The page is read-only. A library skill's row has Show in Library, which opens Library with that skill selected and previewed; any other row has Show in System, which opens System's page, where deployments are removed, drift is resolved, and importables are imported. Folders without a `SKILL.md` and folders whose inspection failed are not listed, as on System's page, and importables are known only after Global's first scan since launch.

### Drift

A deployment drifts when its copies or its library skill no longer match the digest it was written with. A rescan records which copies changed and which are missing; a copy that can no longer be read as a skill counts as changed, and a recorded copy the scan reached under another name, such as through a linked agent directory, is checked directly. The library side is compared at once, against the library skill's current digest, so accepting a copy into the library makes the skill's other deployments outdated without a rescan. Each deployment on a target page shows its state and its remedies, and each path is marked `changed` or `missing`. The sidebar row of a target with a drifted deployment shows a warning dot instead of its count, and its accessibility label reports how many deployments drifted.

| State | Meaning | Remedies |
| --- | --- | --- |
| Workspace changed | A copy changed; the library skill did not | Restore from library, or Accept into library |
| Outdated | The library skill changed; the copies did not | Update workspace (Update system on Global's page) |
| Conflict | A copy and the library skill both changed | Keep library version, or Keep workspace version |
| Missing | A copy is gone and none changed | Redeploy, or Remove |

Drift never drops a deployment, and SkillBinder never resolves it on its own; an outdated copy also waits for the user. Remedies that write the library version over a changed copy, Restore from library and Keep library version, ask first and list the changed copies. The engine checks the copies again before writing. When a copy's change differs from what the page showed, such as a copy shown as matching that has since been edited, or the state changed, the remedy is refused as stale and nothing is written. As with removal, confirmation covers the listed paths: a further edit to a listed copy before confirming is discarded with it. A missing workspace folder blocks every remedy.

Using the library version writes the library payload over every copy that differs from it, writes missing copies, and records the deployment with the library digest. A replaced copy is set aside beside its path until the database records the write; an unrecorded write puts it back. Accepting a copy, through Accept into library or Keep workspace version, first replaces the library skill's payload with the changed copy through a library journal, keeping the previous payload in an app-local backup under `backups/drift`. The library change stays uncommitted until Sync. The deployment's other copies are then rewritten from the accepted version. Copies that changed in different ways, or a blocked copy, cannot be accepted.

### Importable skills

A target page lists the importable skills its last saved scan found, `<n> importable`: skills whose content matches no library skill, each with its slug, validation result, and every path that holds it. Copies merge only when their slug, digest, and validation result match, so a blocked copy never hides an importable one. A recorded copy that changed belongs to its deployment's drift and is not importable. Importables are scan observations kept in engine memory, like Discovery results, and are listed again by the rescan on launch or when the page opens. One that a library skill now matches, for example after an import from Discovery, is no longer listed.

Import runs the same reviewed import plan as Discovery. It inspects the first path again, refuses as stale when the content or validation result differs from what the page showed or when the scan no longer lists it, and prepares a plan that expires after 300 seconds. Invalid metadata needs the acknowledgement checkbox, and blocked skills cannot be imported. A missing workspace folder blocks Import. The review dialog says that the copies stay in place and become the skill's deployment. Applying the plan copies the skill into the library, uncommitted until Sync, then records the target's copies that still hold the imported digest as the skill's deployment, without rewriting them; a copy changed after review is left out and becomes importable again at the next rescan. Copies inside a workspace nested in the target by then are left to that workspace. A workspace removed before the plan is applied gets no deployment, and a target that already holds the skill keeps its deployment. If the recording fails, or the application stops between the import and the recording, the import stands, the failure is logged, and the next rescan records the copies, because they match a library skill. Replaying the plan returns its first outcome.

These are the only writes outside the library, and they reach only target agent skill directories and recorded paths. A recorded path is refused unless it is a named entry inside the workspace folder, or inside a registry global skill directory for Global, after resolving links in its existing parent. Writes run on the engine worker, never on the GPUI thread, behind a deployment journal saved before the first write. Recovery on launch undoes a write the database did not record, deleting only its scratch copies and copies that still hold its bytes and putting back the copies it replaced, and finishes an interrupted removal without deleting a changed copy the user did not confirm. If such a copy's path was filled again before recovery, the changed copy is kept beside it as `<slug>.skillbinder-kept-<journal>` and logged, so recovery never blocks launch.

## Discovery

The retained registry covers 79 agents. Templates expand home and environment defaults. Shared physical skill directories list every reader label. Discovery searches Global and the direct workspace skill directories of every workspace whose folder exists, not arbitrary document folders. Global and workspace traversal have separate depth, entry, exclusion, and mount policies. Links are limited to 16 hops, including links inside discovery locations before physical-path deduplication. Source aliases retain their original path for import revalidation. Discovery is read-only and never changes deployments.

Each discovered skill appears once per slug and content digest, listing every location where those bytes were found, such as `~/.claude/skills/review` and `~/Documents/workspace/.agents/skills/review`, with the readers of each location. The same slug with different content stays a separate entry. Content alone does not merge entries, because the slug becomes the library skill's identity. Copies also merge only when their validation results match: the digest leaves out entries that inspection blocks or excludes, so a copy with an external link stays a separate, blocked entry instead of hiding an importable copy.

Discovery supports start, current results, cancellation, and rescan. There is at most one active worker. Cancelled and failed findings remain visible but cannot be imported. A terminal run expires after 600 seconds; active workers never expire. The UI pages by 50 candidates and supports page selection and invalid-metadata acknowledgement. Identical managed content is hidden separately using inspected current payload bytes rather than cached metadata digests; the status line counts hidden entries, not their locations, as "N already in library". Distinct content sharing a slug remains visible. Unreadable or blocked managed payloads cannot hide a discovered source. A failed worker launch becomes a retained failed run and permits retry. Detailed scan exclusions and failures belong in redacted logs.

## Reviewed imports

Preparation re-inspects opaque selected candidates and creates a durable immutable plan valid for 300 seconds. An entry with several locations imports from the first location the scan found; its content and validation match the others, and review shows that location as the source. Blocked payloads are refused; invalid metadata requires acknowledgement. Review shows source, destination, validation, size, and duplicate handling. Pending application prevents dismissal. The result survives navigation and restart until dismissed.

Application rechecks source identity, source paths, manifests, library revision, and the actual managed catalog. Every source is staged before the first managed move. Internal links become regular entries. Sources remain byte-identical. Content identical to a library skill is reported as already in the library and copies nothing; distinct content sharing a slug creates a separate managed copy. Applying a completed plan returns the stored result, including after restart or plan expiry.

Payload policy preserves the captured limits, portable names, Unicode case collisions, YAML restrictions, plugin exclusions, executable flags, and explicit directories. The canonical digest is `sha256:` followed by the schema-1 manifest hash.

## Library and organization

Library supports text search, flat folder pages opened from the sidebar, multi-selection, assignment and Remove from folder, folder creation and rename, and revision-checked deletion previews. Deleting a folder leaves its skills in the library without a folder. Folders keep a user-defined order and an optional color from a fixed eight-color palette. New folders are appended last without a color. Reordering requires every current folder exactly once, and positions are renumbered densely after each organization change. Names are trimmed and unique under NFKC plus full Unicode case folding. Portable tags remain stored and validated without tag-management UI.

Skill details show validation, counts, the deployment targets that hold the skill (System, for Global, first, then workspaces in sidebar order), and bounded file previews. Listing is limited to 5,000 entries and depth 32; text is limited to 128 KiB. Binary and oversized files remain listed with an explanation. Relative-path and canonical containment checks reject traversal and escaping links.

Shared-slug resolution previews the copies, chooses one winner, validates the expected identities and revision, and moves losers to app-local backups outside the Git repository. A library skill that still has deployments cannot leave the library: resolution refuses to discard a deployed copy with a message naming its targets, such as "shared is deployed to Global, web. Remove those deployments before deleting it." Resolution never writes into Global or workspace skill directories.

## Synchronization

Connect, Refresh, Pull, Push, Sync, and Disconnect use a verified absolute Git executable with a 30-second process timeout. Status refreshes every 30 seconds and on window focus. User credential helpers remain available; prompts are disabled and credentials are not stored in application settings. App-owned Git attributes disable filters, line-ending conversion, ident expansion, and working-tree encoding so portable payload bytes survive synchronization. Remote URLs and branches are validated. The selected remote is reconciled with `origin`.

Refresh fetches without committing or merging. Pull is fast-forward only. Divergence and dirty managed files behind the remote require manual reconciliation. A newly initialized, empty, unborn library can adopt a populated remote through explicit Pull or Sync; a durable adoption journal protects its initial metadata.

Imports and organization changes remain uncommitted until explicit Push or Sync. Commits cover only `.skillbinder.json` and `skills/`, including managed files matched by ignore rules. Unrelated staged files block synchronization without changing the index. Sparse checkout prevents unrelated remote paths from materializing. Existing unrelated local files are preserved.

## Durability and diagnostics

One worker owns bundled SQLite and serializes library and Git mutations. Discovery and target scans run on their own threads; the worker only prepares their inputs and saves their results. Journals persist applying or rolling-back direction, next-move intent, and expected physical identity and digest. Deployment writes keep their own journals under `journals/deployments`, with the paths they write and the scratch siblings named after the journal. Recovery completes or reverses interrupted moves before allowing further mutations. Unknown states retain their journal and block writes. Recovery refuses externally changed portable metadata before moving payloads or replacing metadata. A committed database transaction is never rolled back through filesystem-only recovery.

Portable schema 2 stores folders, tags, and skills as maps keyed by identity. Folder order and color are portable fields, so they sync with the library; reads sort folders by position, then name, so duplicate positions from separate edits never block loading. Machine-local metadata, plans, outcomes, workspaces, target agents, deployments, preferences, logs, staging, journals, and backups live in platform-local storage. The former source-observation and workspace-root tables are dropped on open. No old database is migrated.

Logs use a bounded queue, 5 MiB rotation, at most five files, and 14-day retention. Home paths and common credential formats are redacted. Settings reveals only the engine-owned log directory. Safe errors include category, recovery action, retryability, and diagnostic identity.
