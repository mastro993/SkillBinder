# Native feature coverage

The audited shipped baseline is revision `83d55ef789a7cf256021f6620742e0e9021a8312`. Main was fetched and the rewrite branch rebased before reconstruction; that revision remained current. The baseline exposes 29 application operations across the journeys below. The user deferred UI fidelity and polish; functional behavior remains required.

## Setup and lifecycle

Four persisted steps cover prerequisites, source boundaries, optional synchronization, and final library creation. Backward navigation is allowed; forward skipping is refused. Git 2.39 or newer and writable storage are required. Library initialization stages an empty `skills/` directory and a repository before atomically publishing the directory, then reconciles the database with it. Completion is idempotent.

The executable owns the Tokio runtime and process lock. A second launch requests activation of the existing native window through an app-owned local marker. The Linux window uses the `skillbinder` application ID matching its desktop entry; Wayland compositors retain control over whether an activation request raises the window or requests attention. Shutdown cancels discovery and drains durable operations before flushing logs.

## Workspaces

A workspace is a project folder the user adds, which SkillBinder scans for skills. Its canonical path is its identity; its name starts as the folder's last path component, can be renamed, and need not be unique. Workspaces are machine-local SQLite state outside Git. The agents' global skill directories under home, such as `~/.claude/skills`, are not a workspace; the Agents section shows their skills. SkillBinder never writes into a global skill directory or a workspace; adding skills to them is planned with a later redesign.

The Workspaces section's add button opens native directory selection, which issues the same single-use grant valid for 300 seconds. The picked folder adds its projects as workspaces at once: the folder itself when it has an agent workspace skill directory, such as `.claude/skills`, and each direct child that has one, in name order. Hidden and linked children are skipped, so picking `~/Projects` adds `~/Projects/api` and `~/Projects/web` but not a project's own `.agents` folder. A folder where nothing has an agent skill directory is added alone as an empty workspace. The parent folder is not remembered: picking it again adds only the projects not yet added, and a folder whose projects are all added is refused, naming the existing workspace when the folder itself is the only one, and otherwise with "Every project in <folder> is already added." Nested workspaces are allowed. A scan then covers the new workspaces. Removing a workspace forgets it, then scans again; files in the folder are never touched.

An agent folder cannot be a workspace. An agent folder is one whose agent workspace skill directories, those of any registry agent such as `.claude/skills` or `skills`, include a global skill directory the scan reads, as its expanded template or its resolved path, or one at or inside such a directory, such as `~/.claude/skills` itself or a skill folder in it. Like the scan, this counts only directories under home: one that lies outside home, or links out of it, is skipped by the scan and makes no folder an agent folder. A path spelled through a link to home, such as `$HOME` when home itself is reached through a link, counts as inside home, both for environment-variable roots and for link targets. A directory that does not exist yet counts where it would be created, following links as far as they exist, including a link whose target is missing, so `~/agent-data` is an agent folder when `~/.claude` links to it or when `~/.claude/skills` links to `~/agent-data/skills`. A folder's own skill directories are compared with links resolved too, so a project whose `.claude/skills` links to `~/.claude/skills` is an agent folder. The home folder is one through `~/.claude/skills`, and so is a folder that is not hidden, such as `~/.config/opencode` through `skills`. Picking an agent folder skips it but still adds its qualifying direct children. An agent folder among the children of a picked folder is skipped silently, and it still counts as a project, so a folder whose only projects are agent folders, such as `/Users` holding only the home folder, is not added as an empty workspace. When nothing is added, the pick is refused with "Your home folder's skills are shown under Agents." if the home folder was one of the skipped agent folders, and otherwise with "This folder's skills are shown under Agents." A stored workspace that is an agent folder is forgotten when the engine opens on launch; its files are untouched, and the log records it.

A workspace's page shows its folder path, and notes when the folder is missing. The skills a workspace holds are listed in Discovery.

## Scanning

One scan covers every registry agent's global skill directories and every workspace whose folder exists. It walks each global skill directory with the global limits: depth 8 and 5,000 entries per walk. For a workspace it walks only the agent workspace skill directories at the top of its folder, such as `<workspace>/.claude/skills` or `<workspace>/.agents/skills`, with the workspace limits: depth 12, 200,000 entries per walk, the workspace exclusion names, and the mount-boundary stop on Unix. A `SKILL.md` outside a known skill directory, including one in a deeper project's skill directory, is ignored. A skill folder found through several agent directories or workspaces is listed once per physical folder. Each found location records the workspaces whose scan reads it; the list is empty for a global skill directory.

The app refreshes only on launch and when its window regains focus after losing it. A refresh starts a scan unless one is already running, then refreshes the Git status when a remote is connected. Adding or removing a workspace, applying an install, and Rescan in Discovery's header also start a scan. Starting a scan replaces a running one, whose results are discarded, so a scan always covers the workspaces as they were when it started. Found skills are scan observations kept in engine memory, not in the database; the last completed scan stays visible while the next one runs, and counts update when it completes. There is no filesystem watcher and no cancellation. A workspace whose folder is missing stays listed with a warning glyph and is skipped.

## Agent pages

A detected agent's page shows its global skill directory, a "Shared with" line naming, as the Agents section names them, the other detected agents that read the same directory, including through a link inside home such as `~/.claude/skills` pointing to `~/.agents/skills`, and its found skills. Universal's page shows `~/.agents/skills`, a "Used by" line naming the detected universal agents, and the found skills of that directory. The found skills are counted as "1 found skill" or "<n> found skills". They are every skill folder the last scan found in the shown directory, directly or through a link, sorted by slug, marked Installed when their content matches a library skill and otherwise Not installed, Invalid, or Blocked from their validation. Workspace copies are not included, and neither are copies in an agent's further registry roots, such as OpenClaw's `~/.clawdbot/skills` beside its `~/.openclaw/skills`; Discovery still lists them. The page is read-only. An Installed row has Show in Library, which opens that library skill's page; other rows have no action. Folders without a `SKILL.md` and folders whose inspection failed are not listed, and found skills are known only after the first scan since launch.

## Discovery

The retained registry covers 79 agents. Templates expand home and environment defaults. Shared physical skill directories list every reader label. Discovery lists the skills the scan found in the agents' global skill directories and every workspace, not arbitrary document folders. Global skill directories and workspaces are walked with separate depth, entry, exclusion, and mount policies. Links are limited to 16 hops, including links inside discovery locations before physical-path deduplication. Source aliases retain their original path for install revalidation. Discovery is read-only and never writes into a global skill directory or a workspace.

Each discovered skill appears once per slug and content digest, listing every location where those bytes were found, such as `~/.claude/skills/review` and `~/Documents/workspace/.agents/skills/review`, with the readers of each location. The same slug with different content stays a separate entry. Content alone does not merge entries, because the slug becomes the library skill's identity. Copies also merge only when their validation results match: the digest leaves out entries that inspection blocks or excludes, so a copy with an external link stays a separate, blocked entry instead of hiding an installable copy.

Discovery lists the found skills that are not installed, under the lead "Skills found in your agents and workspaces that are not installed." Its status line shows "Scanning…" while a scan runs and counts found entries, not their locations, as "N found · M already installed". A found skill is installed when its content matches a library skill's cached digest. The cache follows reconciliation (see Synchronization), so changes made to `skills/` outside the app are not seen. An entry's identity follows its content, so the entries chosen for install stay chosen across scans that still find them. Failed findings cannot be installed. The UI pages by 50 candidates and supports page selection and invalid-metadata acknowledgement. Distinct content sharing a slug remains visible. A blocked library skill marks no found skill as installed. A failed worker launch becomes a failed scan and permits retry. Detailed scan exclusions and failures belong in redacted logs.

## Reviewed installs

Preparation re-inspects opaque selected candidates and creates a durable immutable install plan valid for 300 seconds. An entry with several locations installs from the first location the scan found; its content and validation match the others, and review shows that location as the source. Blocked payloads and payloads without files are refused, since Git cannot sync an empty directory; invalid metadata requires acknowledgement. The Review install dialog shows source, destination, validation, size, and duplicate handling, with Back and Install actions. Pending application prevents dismissal. The result, "Install finished: N copied, N already installed", survives navigation and restart until dismissed.

Preparation refuses a found skill whose slug the library already holds, compared under NFKC plus full Unicode case folding, with different content: "The library already holds a different skill named <slug>." A directory under `skills/` that is not yet reconciled holds its name too. Selecting two different payloads with the same slug in one batch is refused with "Select only one distinct payload per shared slug in an install batch.", so a library holds one skill per slug. Content identical to any library skill is reported as already installed and copies nothing. Application rechecks plan expiry, the library revision, that no new skill's directory has appeared, source identity, source paths, and manifests. Every source is staged, then every source is inspected again, before the first managed move, so a source that changes while later ones are copied refuses the whole batch. Internal links become regular entries. Sources remain byte-identical. Each installed skill records its install time on this device. Applying a completed plan returns the stored result, including after restart or plan expiry.

Payload policy preserves the captured limits, portable names, Unicode case collisions, YAML restrictions, plugin exclusions, executable flags, and explicit directories. The canonical digest is `sha256:` followed by the schema-1 manifest hash.

## Library and organization

Library supports text search, preset pages opened from the sidebar, preset creation and rename, and revision-checked deletion previews. A preset is a named set of library skills; a skill can be in any number of presets. A preset page lists the skills it holds. Deleting a preset leaves its skills in the library and in their other presets. Presets keep a user-defined order, an optional color, one of a fixed eight-color palette or any custom color, and an icon from a curated set of 40. New presets are appended last without a color and with the folder icon. Reordering requires every current preset exactly once, and positions are renumbered densely after each organization change. Names are trimmed and unique under NFKC plus full Unicode case folding; a duplicate is refused with "Preset names must be unique." Presets, their memberships, and library folders are machine-local: they live in the database, never sync, and never make Sync report changes. Adding skills to a preset and removing them has no UI for now: the engine supports both, each idempotent, and Library has no selection.

Library folders group library skills for browsing only. A skill is in at most one folder, or in none; folders are separate from presets, and nothing applies them. While Library lists every skill, the header shows its folder tabs in place of the breadcrumb: All skills, a one-point divider, each folder in creation order, then Add folder, a plus glyph with an "Add folder" tooltip, in one strip that scrolls sideways when it overflows. Tabs are small ghost buttons with 13-point labels: the chosen one shows the selected fill in the text color, while the others and the Add folder glyph use the muted text color until hovered. All skills is chosen at launch. Choosing a tab narrows the page to that folder's skills, together with search, and the skill count follows; a folder with no skills reads "No skills in <name>". The choice stays while other pages are open, is not part of Back and Forward, and falls back to All skills when the chosen folder is deleted. Preset pages and skill pages keep the breadcrumb, so folder and preset filters never combine. Add folder shows an inline name field in its place, a borderless input in a tab-shaped fill, and double-clicking a folder tab chooses it and edits its name the same way; Enter saves, while Escape, leaving the field, or an empty name cancels. A created folder shows as a skeleton tab until it is saved. A refused name, such as a duplicate, reports its error as preset names do. While another operation runs, Add folder is inactive and Enter leaves the field open with its name. Right-clicking a folder tab opens Rename and Delete…; Delete… asks "Delete <name>? Its N skills stay in the library." and leaves those skills unfiled. All skills has no menu. Folders have no order controls, color, icon, or count. Right-clicking a skill's row or card opens its menu with Move to folder, a submenu of None and each folder with a check on the current one; it is disabled while there are no folders or another operation runs. While All skills is chosen, a filed skill's dates line starts with the folder glyph and the folder's name. Folder names follow the preset name rules, with the refusal "Folder names must be unique.", and folders are renumbered densely after each organization change.

The page starts with a search field with a search glyph and a clear button and the number of listed skills, then, at the trailing edge, a GPUI Kit segmented control with List and Grid segments. Search matches the slug or description, ignoring case, and an empty result shows "No skills match '<query>'". Skills are listed alphabetically by slug, ignoring case. The chosen view is a machine-local preference, List by default, and survives restart. List shows one row per skill: the slug, one description line, its dates, and the skill's presence. Grid shows cards with the slug, two description lines, dates, and presence, in as many columns at least 260 points wide as fit. Clicking a row or card, outside its agent chips and their "+N" chip, or pressing Enter or Space while it has keyboard focus, opens the skill's page; rows and cards show the theme's secondary fill while hovered. Dates read "Installed 3 days ago · Modified 2 hours ago" in the largest whole unit, or "just now" under a minute, and each one's tooltip shows the exact local date and time. Installed is the install time the database records on this device; a skill that arrived through Pull has none and shows only Modified. Modified is when the newest file of the skill's managed copy last changed on this device, read from the file system each time the library is projected, so on another device it reflects that device's checkout.

Presence shows one chip per Agents row whose global skill directory held a copy with the skill's content at the last scan: Universal for the universal agents together, even when only one of them is detected, then each other detected agent in Agents section order. A copy counts when the scan found it in the global skill directory of one of the row's agents, directly or through a link, as on the agent page and in the sidebar counts. Workspace copies are not part of presence, so there are no workspace chips. Each chip is a small secondary tag holding the agent's avatar and its Agents section name. The avatar shows the agent's full-color logo on white when one is bundled, otherwise its monochrome logo or the square terminal glyph in the text color; Universal uses the layers glyph. A chip's tooltip shows the global skill directory, and Universal's adds a line "Used by <names>" naming its agents. Clicking a chip opens that agent's page or Universal's. Three chips show before the rest collapse into a "+N" chip whose tooltip names them. Before the first scan presence reads "Not scanned yet", and a library skill no detected agent holds reads "Not in any agent".

A skill's page shows the skill's `SKILL.md` as GPUI Kit Markdown with selectable text, and its leading YAML frontmatter as a key and value table. The file is read off the GPUI thread when the page opens. Leaving the page discards a read still in flight; the engine still finishes that read, which the preview limits bound. A `SKILL.md` that is binary, oversized, or unreadable shows the preview's explanation instead. An `http` or `https` link opens in the browser; other links, including relative links to the skill's other files, do nothing. Remote images do not load: the app installs no HTTP client, so the skill page makes no network requests. The page is read-only.

Bounded file previews, used by skill pages, list at most 5,000 entries and depth 32; text is limited to 128 KiB. Binary and oversized files remain listed with an explanation. Relative-path and canonical containment checks reject traversal and escaping links.

## Synchronization

Connect, Refresh, Pull, Push, Sync, and Disconnect use a verified absolute Git executable with a 30-second process timeout. Status refreshes with the app, on launch and when the window regains focus, and with Refresh on the Sync page. User credential helpers remain available; prompts are disabled and credentials are not stored in application settings. App-owned Git attributes disable filters, line-ending conversion, ident expansion, and working-tree encoding so portable payload bytes survive synchronization. Remote URLs and branches are validated. The selected remote is reconciled with `origin`.

Refresh fetches without committing or merging. Pull is fast-forward only. Divergence and dirty managed files behind the remote require manual reconciliation. A library without commits, tracked files, or skills can adopt a populated remote through explicit Pull or Sync, which fast-forwards it to the remote. Any local skill blocks adoption; local presets and library folders never do, and they survive it. Before a fetched revision is used, its tree is validated: managed entries must be regular files, mode 100644 or 100755, inside a skill directory `skills/<slug>/`, and skill directory names must be portable and must not collide under NFKC plus case folding. Push and Sync apply the same rules to the staged tree before committing, so a stray file such as `skills/.DS_Store` refuses the commit rather than publishing a revision that later fetches would reject.

The database records the last commit whose skills it reflects. After every Pull or Sync, including a Sync whose push then fails, and when the engine opens, it rehashes only the skill directories that Git reports as changed under `skills/` since that commit, or every one in the tree and in the database when there was none or Git no longer has it, as in adoption, so a Pull interrupted before this step catches up at the next launch. A Push advances the recorded commit without rehashing. An existing directory is inspected and saved; a removed one is dropped. A rehashed skill keeps its install time, folder, and presets. A skill directory that cannot be inspected keeps its previous record; the failure is logged, the recorded commit stays behind, and the next launch retries it. Reconciliation never fails a Pull, Sync, or launch. A skill that arrives through Pull is unfiled, in no preset, and has no install time. A skill that Pull removes loses its preset memberships and its folder; the presets and folders remain. A pulled skill whose payload is invalid or blocked is still a library skill, and its details record the validation status and messages. The same slug installed with different content on two devices surfaces as an ordinary Pull divergence.

Installs remain uncommitted until explicit Push or Sync. Organization changes are never committed. A library without skills publishes an empty first commit. Commits cover only `skills/`, including managed files matched by ignore rules. Unrelated staged files block synchronization without changing the index. Sparse checkout of `/skills/` prevents unrelated remote paths from materializing. Existing unrelated local files are preserved.

## Durability and diagnostics

One worker owns the bundled SQLite database, `skillbinder.db`, through Diesel and serializes library and Git mutations. Scans run on their own threads; the worker only prepares their inputs. Install journals are rows in the database's `journals` table. They persist applying or rolling-back direction, next-move intent, and expected physical identity and digest for each payload move. The final transaction saves the installed skills, records the install outcome, consumes the plan, and deletes the journal row; deleting the row is the commit marker, so the change and its marker share one transaction. Recovery at open rolls an applying journal forward or finishes rolling back one that was rolling back, before allowing further mutations. Unknown states retain their journal and block writes. A committed change is never rolled back.

The library is only its skill directories, `skills/<slug>/`, and a skill's slug is its identity on every device (ADR 0004). The database, `skillbinder.db`, holds everything else about it: presets with their name, position, color, and icon, where a palette color is stored by name and a custom color as `#rrggbb`; preset memberships; library folders and filing; and each skill's cached digest, file count, total bytes, validation details, and install time. Foreign keys are enforced, so dropping a skill removes its memberships and deleting a folder unfiles its skills. When the engine opens, it adds skill directories the database lacks and drops skills whose directory is gone; it trusts the cached facts of the rest. Plans, outcomes, workspaces, preferences, logs, and staging also live in platform-local storage. No old database or library is migrated; a data directory or library from before ADR 0004 must be deleted by hand.

Logs use a bounded queue, 5 MiB rotation, at most five files, and 14-day retention. Home paths and common credential formats are redacted. Settings reveals only the engine-owned log directory. Safe errors include category, recovery action, retryability, and diagnostic identity.
