# Scanning and imports

## Scanning

The retained registry covers 79 agents, and `fixtures/contracts/registry-directories.json` records every skill directory each one reads beside the registry's own: a directory named for the agent, such as `.codex/skills` or `~/.codex/skills`, and ones it shares such as `.claude/skills`. Templates expand home and environment defaults. Shared physical skill directories list every reader label, so a skill found in `.claude/skills` names all the agents that read it, and one found in `~/.codex/skills` names Codex. The scan covers every global skill directory the agents read and every workspace, not arbitrary document folders. Global skill directories and workspaces are walked with separate depth, entry, exclusion, and mount policies. Links are limited to 16 hops, including links inside scanned locations before physical-path deduplication. Source aliases retain their original path for import revalidation. Scanning is read-only and never writes into a global skill directory or a workspace. Only activation writes there, as managed copies (see [Activation](activation.md)), including the copies an import replaces, and the scan skips the hidden `.skillbinder-` staging directories it writes them through.

The scan lists each distinct content of a found skill as a version: one slug and content digest, listing every location where those bytes were found, such as `~/.claude/skills/review` and `~/Documents/workspace/.agents/skills/review`, with the readers of each location. Copies merge into one version only when their validation results also match: the digest leaves out entries that inspection blocks or excludes, so a copy with an external link stays a separate, blocked version instead of hiding an importable copy. A version's identity follows its slug and content, so it is the same in every scan that finds it. The versions of a skill share its key, the slug compared under NFKC plus full Unicode case folding, because the slug becomes the library skill's identity and the library holds one skill per key; content alone never merges different slugs. Among a key's importable versions, those neither blocked nor without files, the scan prefers one: first the one whose Git tree id equals the `skillFolderHash` that the `skills` lock of any of its locations records as published (the global lock for a location an agent reads as a global root, and each reading workspace's project lock), then the one whose first location holds the most recently modified file, then the one found in the most locations; ties keep the first in location order, so the preference is stable across scans. Only the global lock, `~/.agents/.skill-lock.json` or `$XDG_STATE_HOME/skills/.skill-lock.json` when that is set, records that hash; a project's `skills-lock.json` records a different one, so a workspace copy never matches its lock. A skill whose versions are all blocked has no preferred version.

A found skill is in library when its content matches a library skill's cached digest, or when the library holds its slug, compared under NFKC plus full Unicode case folding, whatever its content: once a skill is imported, the library is its source of truth, and an agent's or workspace's older or edited copy is not a new skill, so a skill's other versions are ignored once one is imported. A managed copy is a copy of a library skill, so it is in library and is never offered for import, even after it was edited in place. The cache follows reconciliation (see Synchronization), so changes made to `skills/` outside the app are not seen. A blocked library skill marks no found skill as in library, by its content or by its slug, not even its own managed copies. Library's Scan for skills counts the found skills not in library from the latest completed scan, a skill with several versions once (see [Library and organization](library-and-organization.md)). Failed findings cannot be imported. A failed worker launch becomes a failed scan and permits retry. Detailed scan exclusions and failures belong in redacted logs.

## Scan for skills

Library's Scan for skills opens the Import skills dialog at once, in a frame about as large as the Add skill picker's, reading "Scanning…" with a spinner while it scans every global skill directory and every workspace to completion, replacing a running scan, and prepares one import plan from that scan. The plan holds every found skill not in library, invalid ones marked; a skill whose versions turned blocked or empty, or whose source directory moved or was replaced between the scan and planning, is left out of it, so its row cannot be ticked and the other skills still import. A background scan that completes while the dialog is open does not change it. A scan that finds no skill not in library reads "No new skills found." with Close; a failed scan or preparation reads "Couldn't scan: <reason>" with Close and Retry.

The list has a search field, "Search found skills", which filters rows by slug and description, and the status line "N found · M already in library". Below them come Select all, then the found skills not in library grouped under "Your agents", with the robot glyph, and each workspace, with the code-folder glyph, in sidebar order; a skill found in several places is listed once, under the place of its first version's first location. Each group header has a checkbox and the group's count. Each row has a checkbox, the slug, an Invalid or Blocked tag, and the description. A skill with one version then shows each of its locations as its directory, with home as `~`, and the Agents rows or workspace that read it, then "N files · B bytes" and its validation messages. A skill with several versions shows a ghost "N versions" button with a chevron-right glyph, an arrow-down glyph while open, which lists each version as a GPUI Kit Radio labelled "Modified <relative time>", followed by its validation when it is not valid, such as Invalid or Blocked, joined by " · ", with a secondary "Matches source" tag when it is the version its lock recorded as published, followed by that version's locations, size, and messages; radios of versions that cannot be imported are disabled. "Replaces the copy in <place>." follows the planned version for each copy it replaces. A click on a row outside its versions ticks it. Every importable skill whose planned version is valid starts ticked, up to 500 in display order; invalid ones start unticked, and a skill with no importable version has a disabled checkbox. Select all and a group's checkbox tick that list's importable skills, invalid ones included, until 500 are ticked, or untick them; a partly ticked list's checkbox shows a dash, and a click on it ticks them all. While the search hides ticked rows, the Select all row adds "N selected not shown". Past 500 ticked, the footer reads "Import at most 500 at a time." and Import is disabled; with an invalid skill ticked, it shows "Import skills with invalid metadata", which Import needs. Choosing another version plans that skill again, with the row spinning and every radio disabled meanwhile, and keeps every tick. The primary button reads "Import N skills". Cancel, Escape, and the close button import nothing, and a click outside the dialog does nothing. Unticked skills are offered again, ticked, on the next Scan for skills.

Import closes the dialog and runs the import under the progress strip. When the plan has expired, Import instead prepares the list again with the same ticks and choices, reading "The list changed since the scan. Check it and import again."; the same happens when the engine refuses the import as stale, because the plan expired, the library changed, or a ticked skill's source changed.

## Imports

Preparation plans every found skill not in library, holding the version the dialog chose for it while that version is still found and importable, else the preferred one; two chosen versions of one skill are refused with "Choose one version of <slug> to import." It leaves out the skills the library holds by slug, including directories under `skills/` not yet reconciled, and re-inspects each planned version into a durable immutable plan valid for 300 seconds. A version with several locations imports from the first location the scan found; its content and validation match the others, and the plan names that location as the source. A version that turned blocked or empty since the scan is left out, since Git cannot sync an empty directory; an invalid one is planned and marked. Choosing another version re-inspects only that skill and carries every other item over, under a new plan id that keeps the first plan's library revision and expiry. Application takes the plan and the ticked skills: it refuses no skill with "Choose skills to import.", more than 500 with "Import at most 500 at a time.", a skill twice with "Choose each skill once.", one the plan does not hold with "A chosen skill is not in this import. Scan again.", and a ticked invalid skill without the acknowledgement with "Acknowledge invalid skill metadata before importing." It re-inspects and stages only the ticked skills, so a change to an unticked skill's folder never refuses the import. The progress strip blocks the app until the import's copies are written, then confirms it with `Imported <n> skills` (see [Activation progress](activation-progress.md)); no other result is shown or kept.

A library holds one skill per slug, compared under NFKC plus full Unicode case folding. Content identical to any library skill is reported as already in library and copies nothing. Preparation also reads where each planned copy was published from the `skills` CLI's lock file beside it: a project's `skills-lock.json` for a workspace copy, or the global `~/.agents/.skill-lock.json`, or `$XDG_STATE_HOME/skills/.skill-lock.json` when that is set, for a copy in an agent's global skill directory. The entry named by the copy's slug gives the skill's source when it is a Git repository: `github` entries as `https://github.com/<owner>/<repo>.git`, `gitlab` and `git` entries by their recorded URL, each with its ref and the folder holding its `SKILL.md`. A missing, unreadable, or non-Git entry, such as a local path or a well-known HTTP index, leaves the skill without a source. Application writes each new skill's record, `records/<slug>.toml` (see Records and drift), once the skill's directory has moved into the library and before the database commit, as part of the journal, so recovery finishes or undoes it with the move: the Git tree id of the imported content, and the source learned from the first lock that records one for any location of the imported version, even when that version's content differs from what the lock recorded. A failed import removes the records it wrote, and one an interrupted import leaves is removed when the engine next opens. Application rechecks plan expiry, refusing a missing plan with "Import plan is unavailable. Prepare it again." and an expired one with "Import plan expired. Review it again.", then the library revision and that no new skill's directory has appeared, refusing either change with "The library changed after import review.", then the ticked skills' source identity, source paths, and manifests. Every ticked source is staged, then every source is inspected again, before the first journaled move, so a source that changes while later ones are copied refuses the whole batch. Internal links become regular entries. Sources remain byte-identical. Each imported skill records its import time on this device. Applying a completed plan returns the stored result, including after restart or plan expiry. Preparing a plan deletes the expired ones, which a missing plan's refusal then covers.

Importing a found skill makes it active wherever it was found (ADR 0006): in the active preset for the agents whose own global skill directory held any of its versions, and in each workspace whose scan found one, for the directories it uses that held one. Preparation reads each of those directories again, at the folder named by the skill's slug, and only where the scan found a version in that very folder, so a folder holding no skill, or a skill nested deeper, is never taken for a copy. One holding a copy with the imported version's content is adopted without writing. One holding a copy of another version is replaced, and the Import skills dialog states each replacement under the planned version as "Replaces the copy in <place>.", naming the Agents rows whose agents read the directory, such as Cursor or Universal, or a workspace with the agents that read its directory, as in "api (Claude Code)", or else the directory with home shown as `~`; importing the ticked skill stands in for the conflict prompt. A directory holding nothing under the slug, or anything SkillBinder never adopts, such as a link or a directory holding `.git`, is left as it is, and the skill is not active there; so are a location only another registry root reads and a workspace directory the workspace does not use. The active preset holds the skill for exactly those agents, a specific list that never gains agents, and each workspace for exactly those directories. Other presets are unchanged, and content already in library activates nothing. Application saves these activations in the import's final transaction, with the skills, so recovery finishes them; a workspace removed since review is skipped with the replacements held for it, and any change to the presets refuses the import as a changed library. The copies then follow as for any activation (see [Activation](activation.md)): each replacement is managed with the content the review saw, so it is rewritten with the imported content, while a copy that changed since review is never overwritten and asks as edited. A directory that cannot be written leaves the skill not applied there until a retry or a later scan.

## First boot

Onboarding ends with the library's first import, once the library has been created on the way into it (see [Setup and lifecycle](setup-and-shell.md#setup-and-lifecycle)). The step is titled "Import your skills" (design O1, O2, O4, O5, O7) under the onboarding frame's "SkillBinder · Step N of M". It prepares its import as Scan for skills does, scanning to completion and planning every found skill not in library from that scan (ADR 0009); since no workspace exists yet, that covers your agents' global skill directories alone. It starts at once when the step shows, and again when the app opens at this step. While it scans, the step reads the lead and "Scanning…" with a spinner, with Skip and an inactive "Import skills". A failed scan or preparation reads "Couldn't scan: <reason>" with Skip and Retry. With nothing to import it reads "No skills to import were found in your agents." with Continue. Otherwise it reads the lead "Importing copies these skills from your agents into your library, each staying active for the agents that have it. You can import others later with Scan for skills in Library.", then a bordered summary card with the avatars of the Agents rows whose global skill directories hold the found skills, up to four and then `+N`, and "N skills found in <agents>", naming those rows in the Agents section's order, then a ghost "Review list" button, then Skip and a primary "Import N skills", where N counts the ticked skills. Review list opens the Import skills dialog over onboarding, titled "Import skills", on the step's own list: the search, Select all, the rows with their versions, replacements, and messages, with the dialog's rules. Your agents form one place, so it shows no group header, and there is no status line, since a new library holds nothing. Its footer holds the cap note or the acknowledgement on the left and a primary "Done" on the right, with no Cancel and no Import. Done, Escape, and the dialog's close button keep the ticks, the chosen versions, and the acknowledgement and return to the step, whose "Import N skills" counts them and is the only button that imports; a click outside the dialog keeps it open, as in Library. A version being planned when the dialog closes still reaches the step's list, and the step's Import waits for it. Onboarding also offers skills it would make active nowhere, such as one found only through a link, nested deeper, or in a Git checkout; ticked, they import inactive. Import runs the progress strip and applies the ticked skills into the active preset, which on first boot is Default, so Default holds each imported skill for the agents whose global skill directory held it; it then finishes onboarding into Library. An unticked skill stays out of the library and out of Default. An import refused because the plan expired or the library or a ticked source changed prepares the list again with the same ticks and reads "The list changed since the scan. Check it and import again."; any other refusal shows its error and leaves the step as it was. Skip and Continue finish onboarding into Library without importing. Finishing onboarding with skills in the library, such as one created where a library directory already existed, also makes the library skills your agents already have active in Default, once (see [Activation](activation.md)). Once onboarding finishes, the app refreshes as at launch, scanning every location.

Payload policy preserves the captured limits, portable names, Unicode case collisions, YAML restrictions, plugin exclusions, executable flags, and explicit directories. The canonical digest is `sha256:` followed by the schema-1 manifest hash. Every inspected payload also has a Git tree id, computed exactly as Git stores the materialized directory: files with mode 100644 or 100755, folders as trees, and empty folders left out.
