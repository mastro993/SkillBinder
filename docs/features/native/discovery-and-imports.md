# Discovery and reviewed imports

## Discovery

The retained registry covers 79 agents, and `fixtures/contracts/registry-directories.json` records every skill directory each one reads beside the registry's own: a directory named for the agent, such as `.codex/skills` or `~/.codex/skills`, and ones it shares such as `.claude/skills`. Templates expand home and environment defaults. Shared physical skill directories list every reader label, so a skill found in `.claude/skills` names all the agents that read it, and one found in `~/.codex/skills` names Codex. Discovery lists the skills the scan found in every global skill directory the agents read and every workspace, not arbitrary document folders. Global skill directories and workspaces are walked with separate depth, entry, exclusion, and mount policies. Links are limited to 16 hops, including links inside discovery locations before physical-path deduplication. Source aliases retain their original path for import revalidation. Discovery itself is read-only and never writes into a global skill directory or a workspace. Only activation writes there, as managed copies (see [Activation](activation.md)), including the copies an import replaces, and the scan skips the hidden `.skillbinder-` staging directories it writes them through.

The scan lists each distinct content of a found skill as a version: one slug and content digest, listing every location where those bytes were found, such as `~/.claude/skills/review` and `~/Documents/workspace/.agents/skills/review`, with the readers of each location. Copies merge into one version only when their validation results also match: the digest leaves out entries that inspection blocks or excludes, so a copy with an external link stays a separate, blocked version instead of hiding an importable copy. A version's identity follows its slug and content, so it is the same in every scan that finds it. The versions of a skill share its key, the slug compared under NFKC plus full Unicode case folding, because the slug becomes the library skill's identity and the library holds one skill per key; content alone never merges different slugs. Among a key's importable versions, those neither blocked nor without files, the scan prefers one: first the one whose Git tree id equals the `skillFolderHash` that the `skills` lock of any of its locations records as published (the global lock for a location an agent reads as a global root, and each reading workspace's project lock), then the one whose first location holds the most recently modified file, then the one found in the most locations; ties keep the first in location order, so the preference is stable across scans. Only the global lock, `~/.agents/.skill-lock.json` or `$XDG_STATE_HOME/skills/.skill-lock.json` when that is set, records that hash; a project's `skills-lock.json` records a different one, so a workspace copy never matches its lock. A skill whose versions are all blocked has no preferred version.

Discovery lists the found skills that are not in library, under the lead "Skills found in your agents and workspaces that are not in your library." Its status line shows "Scanning…" while a scan runs and reads "N found · M already in library", where N counts found skills, not their versions or locations, and M counts the found skills that are in library. A found skill is in library when its content matches a library skill's cached digest, or when the library holds its slug, compared under NFKC plus full Unicode case folding, whatever its content: once a skill is imported, the library is its source of truth, and an agent's or workspace's older or edited copy is not a new skill, so a skill's other versions are ignored once one is imported. A managed copy is a copy of a library skill, so it is in library and Discovery does not list it, even after it was edited in place. The cache follows reconciliation (see Synchronization), so changes made to `skills/` outside the app are not seen. Every found skill is listed on one page, in the order of its first version's first location; there is no pagination. Each row has a checkbox labelled with the slug and the chosen version's description. A skill with one version then shows that version's locations as "path · readers", "N files · B bytes", and its validation messages. A skill with several versions shows a ghost "N versions" button with a chevron-right glyph, an arrow-down glyph while open, which lists each version as a GPUI Kit Radio labelled "Modified <relative time>", followed by its validation when it is not valid, such as Invalid or Blocked, joined by " · ", with a secondary "Matches source" tag when it is the version its lock recorded as published, followed by that version's locations, size, and messages. Choosing a radio chooses the version the skill imports. An import takes the chosen version while it is still found and importable, and otherwise the preferred one; radios of versions that cannot be imported are disabled, and the checkbox of a skill whose versions are all blocked is disabled. Select all selects every skill that has an importable version. One import takes at most 500 skills: with more selected, Discovery shows "N skills selected. Import at most 500 at a time." and Review import is disabled. When a chosen version of a selected skill is invalid, an acknowledgement checkbox appears, and Review import stays inactive until it is checked. Expanded rows, version choices, and selections follow keys and version identities, so they survive scans that still find them, and they reset when Discovery is left. Failed findings cannot be imported. A blocked library skill marks no found skill as in library, by its content or by its slug, not even its own managed copies. A failed worker launch becomes a failed scan and permits retry. Detailed scan exclusions and failures belong in redacted logs.

## Reviewed imports

Preparation re-inspects the opaque chosen versions of the selected skills and creates a durable immutable import plan valid for 300 seconds. A version with several locations imports from the first location the scan found; its content and validation match the others, and review shows that location as the source. Blocked payloads are refused with "Blocked payloads cannot be imported." and payloads without files with "A skill without files cannot be imported.", since Git cannot sync an empty directory; invalid metadata requires acknowledgement, and preparing without it is refused with "Acknowledge invalid skill metadata before preparing an import." The Review import dialog shows source, destination, validation, size, and duplicate handling, with Back and Import actions. Import closes the review, and the progress strip blocks the app until the import's copies are written, then confirms it with `Imported <n> skills` (see [Activation progress](activation-progress.md)). The result, "Import finished: N copied, M already in library", survives navigation and restart until dismissed.

Preparation refuses a found skill whose slug the library already holds, compared under NFKC plus full Unicode case folding, with different content: "The library already holds a different skill named <slug>." A directory under `skills/` that is not yet reconciled holds its name too. Preparing two versions of one skill in one batch is refused with "Choose one version of <slug> to import.", so a library holds one skill per slug. Content identical to any library skill is reported as already in library and copies nothing. Preparation also reads where each selected copy was published from the `skills` CLI's lock file beside it: a project's `skills-lock.json` for a workspace copy, or the global `~/.agents/.skill-lock.json`, or `$XDG_STATE_HOME/skills/.skill-lock.json` when that is set, for a copy in an agent's global skill directory. The entry named by the copy's slug gives the skill's source when it is a Git repository: `github` entries as `https://github.com/<owner>/<repo>.git`, `gitlab` and `git` entries by their recorded URL, each with its ref and the folder holding its `SKILL.md`. A missing, unreadable, or non-Git entry, such as a local path or a well-known HTTP index, leaves the skill without a source. Application writes each new skill's record, `records/<slug>.toml` (see Records and drift), once the skill's directory has moved into the library and before the database commit, as part of the journal, so recovery finishes or undoes it with the move: the Git tree id of the imported content, and the source learned from the first lock that records one for any location of the imported version, even when that version's content differs from what the lock recorded. A failed import removes the records it wrote, and one an interrupted import leaves is removed when the engine next opens. Application rechecks plan expiry, refusing a missing plan with "Import plan is unavailable. Prepare it again." and an expired one with "Import plan expired. Review it again.", then the library revision and that no new skill's directory has appeared, refusing either change with "The library changed after import review.", then source identity, source paths, and manifests. Every source is staged, then every source is inspected again, before the first journaled move, so a source that changes while later ones are copied refuses the whole batch. Internal links become regular entries. Sources remain byte-identical. Each imported skill records its import time on this device. Applying a completed plan returns the stored result, including after restart or plan expiry.

Importing a found skill makes it active wherever it was found (ADR 0006): in the active preset for the agents whose own global skill directory held any of its versions, and in each workspace whose scan found one, for the directories it uses that held one. Preparation reads each of those directories again, at the folder named by the skill's slug, and only where the scan found a version in that very folder, so a folder holding no skill, or a skill nested deeper, is never taken for a copy. One holding a copy with the imported version's content is adopted without writing. One holding a copy of another version is replaced, and the review states each replacement as "Replaces the copy in <place>.", naming the Agents rows whose agents read the directory, such as Cursor or Universal, or a workspace with the agents that read its directory, as in "api (Claude Code)", or else the directory with home shown as `~`; confirming the review stands in for the conflict prompt. A directory holding nothing under the slug, or anything SkillBinder never adopts, such as a link or a directory holding `.git`, is left as it is, and the skill is not active there; so are a location only another registry root reads and a workspace directory the workspace does not use. The active preset holds the skill for exactly those agents, a specific list that never gains agents, and each workspace for exactly those directories. Other presets are unchanged, and content already in library activates nothing. Application saves these activations in the import's final transaction, with the skills, so recovery finishes them; a workspace removed since review is skipped with the replacements held for it, and any change to the presets refuses the import as a changed library. The copies then follow as for any activation (see [Activation](activation.md)): each replacement is managed with the content the review saw, so it is rewritten with the imported content, while a copy that changed since review is never overwritten and asks as edited. A directory that cannot be written leaves the skill not applied there until a retry or a later scan.

## First boot

Onboarding ends with the review of the library's first import, once Create library has created it (see [Setup and lifecycle](setup-and-shell.md#setup-and-lifecycle)). It scans your agents' global skill directories only, never a workspace, and prepares importing the preferred version of each skill found there that it makes active for an agent, up to 500 in scan order. It leaves to Discovery the skills the library already holds by slug, including blocked or unreconciled ones, those whose preferred version is invalid, which need acknowledging, those it would make active nowhere, such as a skill found only through a link, nested deeper, or in a Git checkout, and any beyond the first 500. Create library prepares the review at once. The step is titled "Import your skills". Until a review is prepared it reads "SkillBinder can import the skills your agents already have, each staying active for the agents that have it." with Skip and a primary Review skills button; with nothing to import it reads "No skills to import were found in your agents." with Continue; otherwise it reads "Importing copies these skills from your agents into your library, each staying active for the agents that have it. Skills you skip stay in Discovery.", lists the rows of the Review import dialog with their replacements, and offers Skip and a primary Import. Import applies the plan into the active preset, which on first boot is Default, so Default holds each imported skill for the agents whose global skill directory held it, and finishes onboarding; when it fails, the error shows and Review skills prepares the review again. Skip and Continue finish onboarding without importing. Finishing onboarding with skills in the library, such as one created where a library directory already existed, also makes the library skills your agents already have active in Default, once (see [Activation](activation.md)). Once onboarding finishes, the app refreshes as at launch, scanning every location.

Payload policy preserves the captured limits, portable names, Unicode case collisions, YAML restrictions, plugin exclusions, executable flags, and explicit directories. The canonical digest is `sha256:` followed by the schema-1 manifest hash. Every inspected payload also has a Git tree id, computed exactly as Git stores the materialized directory: files with mode 100644 or 100755, folders as trees, and empty folders left out.
