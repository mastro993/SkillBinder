# Synchronization, durability, and diagnostics

## Synchronization

Connect, Refresh, Pull, Push, Sync, and Disconnect use a verified absolute Git executable with a 30-second process timeout. Status refreshes with the app, on launch and when the window regains focus, and with Refresh on the Sync page. User credential helpers remain available; prompts are disabled and credentials are not stored in application settings. App-owned Git attributes disable filters, line-ending conversion, ident expansion, and working-tree encoding so portable payload bytes survive synchronization. Remote URLs and branches are validated. The selected remote is reconciled with `origin`.

Refresh fetches without committing or merging. Pull is fast-forward only. Divergence and dirty managed files behind the remote require manual reconciliation. A library without commits, tracked files, or skills can adopt a populated remote through explicit Pull or Sync, which fast-forwards it to the remote. Any local skill blocks adoption; local presets and library folders never do, and they survive it. Before a fetched revision is used, its tree is validated: managed entries must be regular files, mode 100644 or 100755, inside a skill directory `skills/<slug>/`, or a record `records/<slug>.toml` of mode 100644, and their slugs must be portable and must not collide under NFKC plus case folding; any other file refuses the tree with "Managed files must be skill directories or their records." Push and Sync apply the same rules to the staged tree before committing, so a stray file such as `skills/.DS_Store` refuses the commit rather than publishing a revision that later fetches would reject.

The database records the last commit whose skills it reflects. After every Pull or Sync, including a Sync whose push then fails, and when the engine opens, it rehashes only the skill directories that Git reports as changed under `skills/`, or whose record changed under `records/`, since that commit, or every one in the tree and in the database when there was none or Git no longer has it, as in adoption, so a Pull interrupted before this step catches up at the next launch. A Push advances the recorded commit without rehashing. An existing directory is inspected and saved with the record its `records/<slug>.toml` holds, if that file is readable and valid, and with its drift; one without such a record gets one from its current content (see Records and drift). A removed one is dropped. A rehashed skill keeps its import time, folder, and presets. A skill directory that cannot be inspected keeps its cached facts; the failure is logged, the recorded commit stays behind, and the next launch retries it. Reconciliation never fails a Pull, Sync, or launch. A skill that arrives through Pull is unfiled, in no preset, and has no import time. A skill that Pull removes loses its preset memberships and its folder; the presets and folders remain. A pulled skill whose payload is invalid or blocked is still a library skill, and its details record the validation status and messages. The same slug imported with different content on two devices surfaces as an ordinary Pull divergence.

Imports, updates, reinstalls, and records that reconciliation writes remain uncommitted until explicit Push or Sync. Organization changes are never committed. A library without skills publishes an empty first commit. Commits cover only `skills/` and `records/`, including managed files matched by ignore rules. Unrelated staged files block synchronization without changing the index. Sparse checkout of `/skills/` and `/records/` prevents unrelated remote paths from materializing. Existing unrelated local files are preserved.

## Durability and diagnostics

One worker owns the bundled SQLite database, `skillbinder.db`, through Diesel and serializes library and Git mutations. Scans and source checks run on their own threads; the worker only prepares their inputs and starts the check's thread, and source caches are used by one check or update at a time. A scan that completes while a check runs is checked again once that check ends. Lock files larger than 8 MiB are not read. Import, update, and reinstall journals are rows in the database's `journals` table. They persist applying or rolling-back direction, next-move intent, and expected physical identity and digest for each payload move. The final transaction saves the imported skills, records the import outcome, consumes the plan, and deletes the journal row; deleting the row is the commit marker, so the change and its marker share one transaction. Recovery at open rolls an applying journal forward or finishes rolling back one that was rolling back, before allowing further mutations. Unknown states retain their journal and block writes. A committed change is never rolled back.

The library is its skill directories, `skills/<slug>/`, and their records, `records/<slug>.toml`, and a skill's slug is its identity on every device (ADRs 0004 and 0005). The database, `skillbinder.db`, holds everything else about it, and caches each skill's source, recorded tree, and drift: presets with their name, position, color, and icon, where a palette color is stored by name and a custom color as `#rrggbb`; preset memberships; library folders and filing; and each skill's cached digest, file count, total bytes, validation details, and import time. Foreign keys are enforced, so dropping a skill removes its memberships and deleting a folder unfiles its skills. When the engine opens, it removes records without a skill directory, adds skill directories the database lacks, and drops skills whose directory is gone; it trusts the cached facts of the rest. Plans, outcomes, workspaces, preferences, logs, staging, and source caches also live in platform-local storage. No old database or library is migrated; a data directory or library from before ADR 0004 must be deleted by hand.

Logs use a bounded queue, 5 MiB rotation, at most five files, and 14-day retention. Home paths and common credential formats are redacted. Settings reveals only the engine-owned log directory. Safe errors include category, recovery action, retryability, and diagnostic identity.
