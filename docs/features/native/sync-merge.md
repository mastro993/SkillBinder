# Sync: merging changes from both sides

Part of [Synchronization](sync-and-durability.md#synchronization).

When both sides changed, Sync merges per skill (ADR 0039): each side's changes count by slug from the base, over `skills/<slug>/` and `records/<slug>.toml`. A skill only one side changed takes that side's version; one both sides changed to the same version is no conflict; one both sides changed to different versions is a conflict, which every check lists in the sync snapshot as `conflicts`, with each side's kind and why and the remote's device and time, and which makes the state `needs_resolve`. Sync refuses, writing nothing, until every conflict has a choice of this device's version or the remote's, with "Choose which version to keep of each skill changed on both sides.", and refuses choices for skills that no longer conflict with "The skills changed on both sides changed. Choose again." With them, it commits this device's changes, reads the remote's commit into an index of its own, takes this device's version of each skill only it changed and of each conflict kept from this device, writes the tree, checks it with the same rules a fetch uses, and commits it with the remote's commit as first parent and this device's as second. The merge's message names the device, says why each skill it contributes changed, copied from the newest `SkillBinder-Skill` trailer of this device's unpushed commits, and carries a `SkillBinder-Choice: <slug> local|remote` trailer per choice; with nothing contributed its subject reads "*device*: sync with the remote". The engine then records the merge in the journal, moves the working tree from this device's commit to the merge, moves the branch with a check of its old value, which needs no reflog, forgets the journal row, and pushes, then reconciles, rewrites managed copies, and adopts agent copies as after a Pull. A merge whose tree a fetch would refuse, such as two skill directories whose names collide, is never published: Sync fails, and this device's committed change waits. A merge interrupted after its journal row finishes at once, or at the next launch: with the library still at this device's commit, the managed files are reset to the merge and the branch moved; with the branch already moved, only the row is dropped. Without Git at launch, the library refuses changes until a launch with Git finishes it. Before a fetched revision is used, its tree is validated: managed entries must be regular files, mode 100644 or 100755, inside a skill directory `skills/<slug>/`, or a record `records/<slug>.toml` of mode 100644, and their slugs must be portable and must not collide under NFKC plus case folding; any other file refuses the tree with "Managed files must be skill directories or their records." Push and Sync apply the same rules to the staged tree before committing, so a stray file such as `skills/.DS_Store` refuses the commit rather than publishing a revision that later fetches would reject.

Resolve… opens "Resolve changes on both sides" (Y9): one line naming the device that changed the remote's version, then, per skill changed on both sides, its slug over two radio cards, "This device (*name*)" with why it changed and "Not pushed", and the remote's device with why and when, then how many other skills changed on only one side and merge on their own; its Sync stays inactive until every skill has a choice, and closes the dialog and runs the Sync. Choices last until a Sync or a check changes which skills changed on both sides.
