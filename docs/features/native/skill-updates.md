# Skill updates

How a library skill learns its source, how sources are checked, and how Update, Update all, and the review of one skill's update change it. The library itself is described in [Library and organization](library-and-organization.md).

A library skill without a source learns one after each completed scan when a found copy's Git tree id equals the skill's recorded tree and a `skills` lock entry traces that copy, as importing it would; this covers skills imported before sources were kept and skills that arrived by Pull. Only the database learns the source then, so learning never dirties the library ahead of a Pull; the next Push or Sync that pulls nothing writes it into the skill's record, `records/<slug>.toml`, and commits it, and reconciling a record without a source keeps the learned one. Each lock file is read once per learning pass. A learned source is never removed when the copy goes away, and a copy whose content differs teaches nothing. A library skill with a source is checked for updates after each completed scan, so on launch, when the window regains focus, after an import, an update, or a reinstall, and hourly while the app runs, window open or not, at most once an hour for the same source and recorded tree, on a thread of its own. The check fetches each source repository and ref once, shallow and without blobs, into a cache under application data, takes the skill's folder from the fetched commit, and compares its Git tree id with the skill's recorded tree: an equal tree is up to date without fetching or writing a file, and only a different one is checked out into staging and inspected; the comparison is not with its library content, so a drifted skill has an update only when its source no longer holds its recorded content. Changed content that an update would refuse, because it is blocked, has invalid skill metadata ("The source's current version has invalid skill metadata."), or has no files, reads as a failed check with that reason instead of an update. A skill pinned to a commit is never checked. Checks use the same verified Git as Sync, with prompts disabled and user credential helpers available, a 120-second timeout per fetch, and the app-owned raw attributes in each cache; checks and updates keep separate caches. Results are kept in memory, apply only while the skill's source and recorded tree are unchanged, and are replaced by the next check after launch.

While a skill has an update, its Grid card shows an Update button beside its name, its page header shows one, and its row's context menu offers Update; each opens the skill's [review](#reviewing-one-skills-update) rather than updating at once. Library's header carries an update control before Scan for skills, whatever folder tab or search is chosen: with no update it shows the refresh glyph and checks every source now when clicked, whatever the interval since each last check; while a check runs, however it started, the glyph spins and the control is inert; with at least one update it shows the upload glyph and updates every skill that has one; and while it runs, started here or from the [menu bar menu](menu-bar.md), it shows a circular progress ring whose tooltip counts the skills finished of the total. Update all runs in the client, so closing the window does not stop it. The control is unavailable while another operation or a Git operation runs. Update all applies at once, without review. Each skill updates on its own, and one removed meanwhile counts as failed: its source is fetched again, its folder is checked out and inspected, and content that is blocked, has invalid skill metadata, or has no files is refused, since an update cannot ask for the acknowledgement an import of invalid metadata needs. The skill's new record, the fetched tree with its source, is written by the same journal after the moves and before the database commit, so recovery finishes it with them, and rolling back restores the previous record. New content replaces the skill's directory through a journaled pair of moves, so recovery treats it like an import; when the library content already equals the fetched content, the journal has no moves and only writes the record and saves the drift. A source folder with more than 5,000 files and folders, counted from Git's tree objects before any file is fetched, is refused with "The source's folder has too many files to check.", and one holding a Git submodule with "The source's folder holds a Git submodule, which SkillBinder cannot check out.", since its content would check out as an empty folder. The skill keeps its slug, source, import time, folder, and presets, and the update remains uncommitted until Push or Sync. Afterwards the page shows "Updated N · M failed" until it changes. A skill page shows "Couldn't check for updates: <reason>" when its check failed, "Its source no longer has this skill." when the fetched commit has no folder at the source's path, and "Couldn't update: <reason>" after a failed update. Once the batch ends, the updated skills' managed copies are rewritten (see [Activation](activation.md)); other copies in agents' and workspaces' directories are never written, and an older copy counts as in library, so Scan for skills does not offer it.

## Reviewing one skill's update

Update on one skill opens the "Update <slug>" dialog, at the Import skills dialog's size, and nothing is written until Update is clicked in it ([ADR 0037](../../adr/0037-updating-one-skill-shows-its-changes-first.md), [design](../../design/skill-update-diff/README.md)). While the source is fetched, the body reads "Fetching <slug> from its source…" with a turning glyph and Update is inactive. The engine fetches the source as Update does, checks the skill's folder out into staging, inspects it and refuses what an update would, and compares the skill's current library content, read from disk, with the fetched content; staging is removed once the review is built. The dialog then lists every added, changed, and removed file sorted by path in one scrolling list, unified lines only, drawn by the design system's `DiffView`, GPUI Kit's `Diff`: each file has a header with a fold chevron, an A, M, or D mark, its path relative to the skill folder in mono, and "+A −D", every file starts unfolded, lines show old and new line numbers and `+` or `−` marks on Kit's change backgrounds, and unchanged stretches past three lines of context fold into "<N> unchanged lines", which unfold on click. A renamed file shows as removed and added, and a changed executable bit shows as Kit's `old mode` and `new mode` lines. Under the title, a muted line shows the source repository's glyph, its repository and folder in mono, then "· <N> files changed · +<A> −<D>" in the success and danger colors. The footer reads "Nothing changes until you update." with Cancel and Update. The engine builds the patch in-process with `similar`, each text file with its whole text as context. Some files show one muted line under their header in place of lines, and start folded so GPUI Kit's own summary of a file without lines stays hidden: a file with a NUL byte in its first 8,000 bytes, or not UTF-8, on either side reads "Binary file changed", followed by "· 18 KB → 21 KB" when both sides have it; a text file over 128 KiB on either side, the skill page's preview limit, reads "Too large to show (over 128 KiB)"; and once the next file's lines would take the patch past 4 MiB, that text file and every later text file within the limit read "Not shown: this update's changes are too large to show in full.". These files count no lines in the figures, and the patch carries only their headers, plus Git's "Binary files … differ" line for a binary one. When the skill's library content differs from its record, such as after an edit made outside SkillBinder, a warning notice above the files reads "<slug> was changed outside SkillBinder. Updating replaces those changes too; they show as removed lines.", and those edits show as removed lines, since the review compares the library content as it is now. When the review fails, the body shows a danger notice "Couldn't fetch <slug>'s source: <reason>" and Update stays inactive: a fetch Git could not finish gives Git's user-safe reason ("Git could not read the source. Check access and the repository.") with a Retry button that fetches again, while content an update would refuse (blocked, invalid skill metadata, no files, a submodule, over 5,000 entries, or a source that no longer holds the skill) gives the update's own text without Retry. An error from Update itself before anything is fetched, such as Git going missing, shows its own text in that notice, without the prefix or Retry.

The review carries the digest of the library content it started from and the fetched tree. Update fetches the source again and checks it out: when the fetched tree and the library content's digest still equal the reviewed ones, it replaces the skill exactly as Update does, with the same journal, record, managed copies, and scan, and the dialog closes and the page shows "Updated 1 · 0 failed", or "Couldn't update: <reason>" after a failure. Otherwise it writes nothing and the dialog shows the changes from that same checkout with an info notice: "<slug>'s source changed while you were reviewing. These are its newest changes; review them, then update." when the source moved, checked first, or "<slug> changed in your library while you were reviewing. These are the changes now; review them, then update." when the library content moved, such as by a Pull; Update must be clicked again. While Update runs it reads "Updating…", and Cancel, Escape, the backdrop, and the close button do nothing; otherwise each of them discards the review, and Enter on the dialog never confirms it. While a blocking change, an import, Update all, or a Git operation runs, the dialog's Update is inactive, and it becomes active again when that work ends.
