# MCP server

`skillbinder mcp` serves the [command line tool](command-line.md)'s actions to agents as MCP tools over stdio ([spec](../../specs/mcp-server.md); ADR 0025). Each tool call becomes the request its command sends, over the same socket, so the app runs it under the command's rules and the window shows it. Slice M0 (#205) ships the server and the library, preset, and copy tools; M1 (#206) adds workspaces, agents, Explore, import, updates, and Sync; M2 (#207) connects agents from Settings.

## Connecting

Settings › Agents › MCP server connects Claude Code, Codex, VS Code, and Cursor in one click each, through each agent's own installer, and copies the configuration for any other agent ([Settings › Agents](settings-agents.md#mcp-server), ADR 0026). SkillBinder never writes an agent's settings. By hand, an agent is pointed at the installed command:

```sh
claude mcp add --scope user skillbinder -- skillbinder mcp
```

or, for any agent, `{"mcpServers": {"skillbinder": {"command": "skillbinder", "args": ["mcp"]}}}` in its MCP settings. The server answers the handshake and `tools/list` without touching the app; the first tool call connects to it, starting it in the background when it isn't running, as the command does.

## Tools

They list in this order. Reading tools are read-only and idempotent; the rest are destructive, but `install_skills`, which only adds skills to the library. `set_skills_active`, `switch_preset`, and `choose_agent` are idempotent. Tools that reach the network are open-world: `find_skills`, `install_skills`, `update_skills`, `sync_library`, and `manage_repositories`.

| Tool | Arguments | Command |
| --- | --- | --- |
| `status` | | `status` |
| `list_skills` | `filter` (`all`, `active`, `inactive`, `updates`), `folder` | `skills` |
| `get_skill` | `skill_slug` | `skill` |
| `list_places` | `kind`: `presets`, `folders`, `copies`, `workspaces`, `agents`, or `repositories` | `presets`, `folders`, `copies`, `workspaces`, `agents`, `repos` |
| `find_skills` | `where` (`explore` with `query`, or `found`) | `search`, `scan` |
| `set_skills_active` | `skill_slugs`, `active`, `preset` (the active one when left out) or `workspace`, `agents`, `replace` | `enable`, `disable`, `preset add`, `preset remove`, `workspace enable`, `workspace disable` |
| `switch_preset` | `preset`, `replace` | `preset activate` |
| `organize_library` | `action` (`create_preset`, `rename_preset`, `clone_preset`, `delete_preset`, `create_folder`, `rename_folder`, `delete_folder`, `file_skills`), `name`, `new_name`, `skill_slugs`, `folder`, `confirm` | `preset …`, `folder …` |
| `manage_workspace` | `action` (`add` with an absolute `path`, `rename`, `remove`), `workspace`, `new_name`, `replace`, `confirm` | `workspace add`, `rename`, `remove` |
| `choose_agent` | `agent`, `on`, `replace` | `agent on`, `agent off` |
| `install_skills` | `refs`, as `find_skills` gives them | `install` |
| `import_skills` | `skills` (`slug`, optional `version`) or `all`, `replace` | `import` |
| `update_skills` | `action` (`check`, `update` with `skill_slugs` or `all`, `reinstall` with one skill in `skill_slugs`) | `updates --check`, `update`, `reinstall` |
| `sync_library` | `action` (`sync`, `push`, `pull`, `set_remote` with `url` and `branch`, main by default, `remove_remote`) | `sync`, `push`, `pull`, `remote …` |
| `manage_repositories` | `action` (`add`, `remove`, `install_all`), `repository` (a URL, or `<owner>/<repo>` once added) | `repo …` |
| `resolve_copies` | `action` (`replace`, `keep`, `retry`), `copies` (`skill_slug`, `directory`) | `copies …` |

Reading tools, and `update_skills` for its check, take `response_format`: `concise`, the default, leaves out descriptions, sources, and recorded content ids; `detailed` returns the command's `--json` rows as they are. Lists go under their name beside `more`, at most 200 entries: `find_skills` returns `found` for a scan, and `results` with `skills_sh` for a search. `update_skills` returns its check's `skills` (at most 200, beside `more`) and `unchecked`, or what an update did. Every result also carries the command's text. Removing skills from a preset other than the active one, or turning them off in a workspace, takes no `agents`, as `preset remove` and `workspace disable` don't.

The server's working folder means nothing to the agent, so a workspace is named by its name or by an absolute path inside it; a value that can only be a relative path (`.`, `..`, or one starting `./`, `../`, or `~/`) returns `usage` before the app hears of it, and anything else is a name, which may hold `/` or start with `~`. `manage_workspace` `add` needs an absolute path. The server's instructions add that `install_skills` leaves skills inactive until `set_skills_active` turns them on.

## Questions

The server's instructions tell agents to read first and to pass `replace` or `confirm` only after the user said so; neither is ever assumed. Questions asked before anything changes are a deletion's or a workspace removal's, answered by `confirm`, and an import's that replaces copies, answered by `replace`.

- **A client that shows forms, before protocol 2026-07-28.** The app's question, such as "Replace your copy of pdf in ~/.claude/skills?", "Delete Work? Its 3 skills stay in the library.", or "Import 1 skill and replace 1 copy?" after the copies it replaces, goes to the user mid-call as a form with one required Yes box. Only Accept with Yes ticked is yes; declining, cancelling, or leaving it unticked keeps the copy waiting or changes nothing.
- **A client that shows forms, on protocol 2026-07-28.** The call runs asking, and the server answers no to each of the app's questions, keeping them; it returns an input-required result with one form per question and what it asked as its request state, and nothing waits in the app. On the client's retry, each copy answered yes is replaced and the rest wait; a confirmed deletion or import runs again, answering yes only to the very question the user saw, so a library that changed in between returns `conflict` and changes nothing. A declined deletion or import never reaches the app again.
- **A client that can't.** Copies a change left waiting come back under `waiting` with `needs_answer`, "1 copy needs the user's answer." and the hint "Ask the user, then call resolve_copies with action replace, or ask them to review it in SkillBinder."; calling the change again would find it done. A deletion or a workspace removal returns `needs_answer` with the app's question and "Ask the user, then call again with confirm: true.", and an import that replaces copies the app's list of them and "Ask the user, then call again with replace: true."

## Results and errors

A failure is a tool error whose structured content is the command's `--json` failure document: `error` with its `code`, `message`, and `hint`, and `result` when part of a change landed. Output schemas mark the concise-only omissions optional and leave out schemars' integer formats, which clients don't know. Progress the app reports goes out as progress notifications when the call has a progress token, with `Switching to Work…` or `Updating skills…` as the message; a change while another runs, such as a second Update all, returns `busy`. A cancelled call stops waiting and gets no response, while the app finishes the change.

## The app's lifetime

From the first request the app welcomes, the server holds one idle connection (`Request::Hold`), opened before that request is sent and counted by the app from its greeting, so the request's own connection can't close first; the app counts it as a connected command so an app it started in the background stays up for the agent's session rather than starting for every call, and quits when the session ends and nothing else shows it. A hold that closes because the app quit opens again with the next call.
