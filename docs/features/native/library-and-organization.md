# Library and organization

Library supports text search, preset creation, rename, and clone, and revision-checked deletion previews. A preset is a named configuration of library skills for your agents, holding each skill for all your agents or for specific ones; a skill can be in any number of presets. Presets are activated from the sidebar and have no page of their own. Deleting a preset leaves its skills in the library and in their other presets; deleting the active preset activates the Default preset in the same change, and its confirmation states the skills that adds and removes for your agents (see [Activation](activation.md)). Every library starts with the Default preset, which always comes first and which the app never deletes, renames, colors, gives another icon, or moves. Presets keep a user-defined order, an optional color, one of a fixed eight-color palette or any custom color, and an icon from a curated set of 40. New presets are appended after the Default preset, are empty, and have no color and the layers icon. Creating a preset adds its row at once; a refused creation removes it and shows an error toast. Cloning likewise adds the copy row at once and removes it with an error toast if the clone is refused. Reordering requires every current preset exactly once, keeps the Default preset first so no other preset can move above it, and renumbers positions densely after each organization change. Names are trimmed and unique under NFKC plus full Unicode case folding; a duplicate is refused with "Preset names must be unique." Presets, their memberships with each skill's agents, the active preset, and library folders are machine-local: they live in the database, never sync, and never make Sync report changes.

One preset is active at a time, and its skills are what SkillBinder writes into your agents' global skill directories as managed copies (see [Activation](activation.md)). The app starts with the Default preset active, and clicking a preset activates it in place without opening a page: its row shows active at once while the engine saves the choice and writes and removes copies to match it. The engine keeps the choice, so it persists across restarts, and a preset that no longer exists reads as the Default preset. Library keeps listing every library skill. The sidebar gives the active preset a fainter fill than the route selection: its color at low opacity, or a muted selection fill when it has no color. Each preset row ends with the number of skills it holds, and the active one shows a check after its name in the same color as its icon, at a heavier stroke than the section glyphs. A library skill joins or leaves the active preset from the Active checkbox on its row or card and in its page header, or from its row's context menu, whose "Active in <name>" row is checked while the skill belongs to it; joining holds it for all your agents. The agents button beside the checkbox chooses which of your agents the active preset holds it for. Each change saves immediately like every organization change, and the copies follow it. While the active preset holds no skills, Library shows the notice "No skills active in <name>". A workspace's page lists the same skills with controls that edit the workspace instead (see [Workspace activation](workspace-activation.md)).

Rename edits a preset's name inline; pressing Enter shows the new name at once while the engine saves it. A refused rename restores the stored name and shows an error toast with the reason. Right-clicking any preset, including Default, opens Clone, which copies the preset's color, icon, name prefixed with "Copy of", and skills with their agents into a new editable preset directly after it. A taken copy name gains a numeric suffix, such as "Copy of Review 2". Default's menu holds only Clone; the app still never renames it, recolors it, re-icons it, moves it, or removes it.

Library folders group library skills for browsing only. A skill is in at most one folder, or in none; folders are separate from presets, and nothing applies them. While Library lists every skill, the header shows its folder tabs in place of the breadcrumb: All skills, a one-point divider, each folder in its stored order, then Add folder, a plus glyph with an "Add folder" tooltip, in one strip that scrolls sideways when it overflows. Tabs are small ghost buttons with 13-point labels: the chosen one shows the theme's muted fill, light gray in the light theme and dark gray in the dark theme, in the foreground color, while the others and the Add folder glyph use the muted text color until hovered. All skills is chosen at launch. Choosing a tab narrows the page to that folder's skills, together with search; a folder with no skills reads "No skills in <name>". The choice stays while other pages are open, is not part of Back and Forward, and falls back to All skills when the chosen folder is deleted. Skill pages keep the breadcrumb; presets never filter Library, so folder and preset choices cannot combine. Add folder shows an inline name field in its place, a borderless input in the chosen tab's fill, and double-clicking a folder tab chooses it and edits its name the same way; Enter saves, while Escape, leaving the field, or an empty name cancels. A created folder's tab shows at once, after the other folders, while it is saved; a refused one disappears and its error is reported. A refused name, such as a duplicate, reports its error as preset names do. While another operation runs, Add folder is inactive and Enter leaves the field open with its name. Right-clicking a folder tab opens Rename and Delete…; Delete… asks "Delete <name>? Its N skills stay in the library." and leaves those skills unfiled. All skills has no menu. Folder tabs reorder by dragging exactly as presets do, sideways: the dragged tab lifts into a floating tab with a shadow that follows the pointer, which shows a closed hand until release, leaving its slot empty. Once the floating tab's leading edge passes the middle of a neighbouring tab and the gap after it, the tabs it passes slide 180 milliseconds aside to show the order a drop would save. Releasing the pointer anywhere saves that order, and the floating tab settles into its slot; releasing it on itself does not choose it. The new order is shown while it is saved, and a save that fails, or one refused while another operation runs, slides back to the stored order. Reduced motion moves tabs without sliding. All skills and Add folder do not move. New folders are appended last, and reordering requires every current folder exactly once. Folders have no color, icon, or count. Right-clicking a skill's row or card opens its menu with Move to folder, a submenu of None and each folder with a check on the current one; it is disabled while there are no folders or another operation runs. While All skills is chosen, a filed skill's folder line shows the folder's name. Folder names follow the preset name rules, with the refusal "Folder names must be unique.", and folders are renumbered densely after each organization change.

The page starts with a search field with a search glyph and a clear button, and, at the trailing edge, a GPUI Kit segmented control with List and Grid segments. Search matches the slug or description, ignoring case, and an empty result shows "No skills match '<query>'". Skills are listed alphabetically by slug, ignoring case. The chosen view is a machine-local preference, List by default, and survives restart. The header's trailing Import icon button, labelled by its tooltip, opens Discovery, where copies found on this device are reviewed before they join the library. List wraps every row in one card with a hairline border and 10-point corners, on the page's own surface, lifted a step above it in the dark theme; the card's rows are divided by hairlines inset 14 points from both edges and padded 11 by 14 points. A row shows the slug, then one muted line holding its folder while Library lists every skill, then one description line, with the activation controls, the Active checkbox and the agents button, at its trailing edge, then the skill's agents line. Grid shows tiles on the list card's own surface and hairline with 12-point corners, each holding the slug with its glyphs and Update button, then the same muted line, two description lines, and a footer with the agents line at its leading edge and the activation controls at its trailing edge, in as many columns at least 260 points wide as fit. A skill with an update shows a warning-colored upload-circle glyph after its slug, with the tooltip "Update available". A drifted skill's row or card shows a warning-colored alert-circle glyph after its slug, with the tooltip "Changed outside SkillBinder" (see Records and drift). Clicking a row or tile, outside its activation controls, agent avatars, their "+N" circle, and warning glyph, or pressing Enter or Space while it has keyboard focus, opens the skill's page, while Enter or Space on its focused Active checkbox toggles the checkbox instead; rows and tiles show the theme's muted fill while hovered.

The agents line shows an avatar for each Agents row whose global skill directory holds the skill's applied managed copy, Universal first, then a warning-colored alert-circle glyph while any of the skill's copies is in another state than applied, whose tooltip counts the copies that need review and whose click lists them in the Skill copies dialog; with neither, it reads "Not in any agent". Library's agents line shows only your agents' copies, and a workspace's page shows that workspace's; the glyph counts a skill's copies everywhere. [Activation](activation.md) describes the avatars, the agents menu, and the dialog.

A skill's page shows the skill's `SKILL.md` as GPUI Kit Markdown with selectable text, and its leading YAML frontmatter as a key and value table. The file is read off the GPUI thread when the page opens. Leaving the page discards a read still in flight; the engine still finishes that read, which the preview limits bound. A `SKILL.md` that is binary, oversized, or unreadable shows the preview's explanation instead. An `http` or `https` link opens in the browser; other links, including relative links to the skill's other files, do nothing. Remote images do not load: the app has no HTTP client, so the skill page makes no network requests. The page is read-only. Its header starts with the activation controls, and while any of the skill's copies is in another state than applied, the page shows how many need review in the warning color with a Review button (see [Activation](activation.md)).

Bounded file previews, used by skill pages, list at most 5,000 entries and depth 32; text is limited to 128 KiB. Binary and oversized files remain listed with an explanation. Relative-path and canonical containment checks reject traversal and escaping links.

## Skill updates

A library skill without a source learns one after each completed scan when a found copy's Git tree id equals the skill's recorded tree and a `skills` lock entry traces that copy, as importing it would; this covers skills imported before sources were kept and skills that arrived by Pull. Only the database learns the source then, so learning never dirties the library ahead of a Pull; the next Push or Sync that pulls nothing writes it into the skill's record, `records/<slug>.toml`, and commits it, and reconciling a record without a source keeps the learned one. Each lock file is read once per learning pass. A learned source is never removed when the copy goes away, and a copy whose content differs teaches nothing. A library skill with a source is checked for updates after each completed scan, so on launch, when the window regains focus, and after an import, an update, or a reinstall, at most once an hour for the same source and recorded tree, on a thread of its own. The check fetches each source repository and ref once, shallow and without blobs, into a cache under application data, takes the skill's folder from the fetched commit, and compares its Git tree id with the skill's recorded tree: an equal tree is up to date without fetching or writing a file, and only a different one is checked out into staging and inspected; the comparison is not with its library content, so a drifted skill has an update only when its source no longer holds its recorded content. Changed content that an update would refuse, because it is blocked, has invalid skill metadata ("The source's current version has invalid skill metadata."), or has no files, reads as a failed check with that reason instead of an update. A skill pinned to a commit is never checked. Checks use the same verified Git as Sync, with prompts disabled and user credential helpers available, a 120-second timeout per fetch, and the app-owned raw attributes in each cache; checks and updates keep separate caches. Results are kept in memory, apply only while the skill's source and recorded tree are unchanged, and are replaced by the next check after launch.

While a skill has an update, its Grid card shows an Update button beside its name, its page header shows one, and its row's context menu offers Update. Library's header carries an update control beside Import, whatever folder tab or search is chosen: with no update it shows the refresh glyph and checks every source now when clicked, whatever the interval since each last check; while a check runs, however it started, the glyph spins and the control is inert; with at least one update it shows the upload glyph and updates every skill that has one; and while it runs it shows a circular progress ring whose tooltip counts the skills finished of the total. The control is unavailable while another operation runs. Update and Update all apply at once, without review. Each skill updates on its own, and one removed meanwhile counts as failed: its source is fetched again, its folder is checked out and inspected, and content that is blocked, has invalid skill metadata, or has no files is refused, since an update cannot ask for the acknowledgement an import of invalid metadata needs. The skill's new record, the fetched tree with its source, is written by the same journal after the moves and before the database commit, so recovery finishes it with them, and rolling back restores the previous record. New content replaces the skill's directory through a journaled pair of moves, so recovery treats it like an import; when the library content already equals the fetched content, the journal has no moves and only writes the record and saves the drift. A source folder with more than 5,000 files and folders, counted from Git's tree objects before any file is fetched, is refused with "The source's folder has too many files to check.", and one holding a Git submodule with "The source's folder holds a Git submodule, which SkillBinder cannot check out.", since its content would check out as an empty folder. The skill keeps its slug, source, import time, folder, and presets, and the update remains uncommitted until Push or Sync. Afterwards the page shows "Updated N · M failed" until it changes. A skill page shows "Couldn't check for updates: <reason>" when its check failed, "Its source no longer has this skill." when the fetched commit has no folder at the source's path, and "Couldn't update: <reason>" after a failed update. Once the batch ends, the updated skills' managed copies are rewritten (see [Activation](activation.md)); other copies in agents' and workspaces' directories are never written, and Discovery treats an older copy as in library.

## Records and drift

Every library skill has a record, `records/<slug>.toml` beside `skills/`, which syncs with it (ADR 0005). It holds `tree`, the 40-digit hexadecimal Git tree id of the content the skill should have, and an optional `[source]` table with the source's `url`, `ref`, and `path`. Importing, updating, and reinstalling write it; users never edit library skills. Reconciliation (see Synchronization) reads the record of each skill it inspects. A skill without a readable, valid record gets one from its current content, without a source. The database caches it at once, and its file is written into `records/` by the next Push or Sync that finds nothing to pull, which commits it; written earlier, it would dirty the library and block a Pull of what other devices pushed. Source learning also considers a found copy the library holds by slug, and a Lost skill that learns a source becomes Restorable. The database migration that added records forgets the reconciled commit, so every skill is rehashed once, and every open also rehashes the skills whose record is not cached yet, even in a library without a commit, so skills imported before records existed get theirs.

A skill has drifted when its inspected content's tree differs from its record's, such as after a Pull of content whose record did not change. It is Restorable when the library's Git objects hold the recorded tree or the record has a source, and otherwise Lost. Copies in agents and workspaces never make a skill drift. A drifted skill's page shows, in the warning color, "Changed outside SkillBinder. Reinstall restores the content its record holds." when it is Restorable, and "Changed outside SkillBinder. Neither the library's history nor the skill's source holds its recorded content any more, so it can't be reinstalled." when it is Lost. A Restorable skill's page header has a Reinstall button, before Update when both show. Reinstall restores the recorded tree from the library's own Git objects, checking it out through a scratch bare repository that borrows them through `objects/info/alternates`, so the library's index and working tree are untouched. Otherwise it fetches the source as an update does and uses its folder only when the folder's current tree equals the recorded one, and when neither holds it, Reinstall fails with "Neither the library's history nor the skill's source holds its recorded content." The skill is then marked Lost, so its page no longer offers Reinstall. Reinstall never moves a skill to newer content. Its replacement is one journal exactly like an update's, record included. A reinstall remains uncommitted until Push or Sync; it rewrites the skill's managed copies, and a scan runs after it. The skill's page then shows its restored content. Drift is only found when the library is reconciled, so an edit inside the library folder is noticed once Git reports it as changed, such as after a Pull.
