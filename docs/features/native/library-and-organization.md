# Library and organization

Library supports text search, preset pages opened from the sidebar, preset creation and rename, and revision-checked deletion previews. A preset is a named set of library skills; a skill can be in any number of presets. A preset page lists the skills it holds. Deleting a preset leaves its skills in the library and in their other presets. Every library starts with the Default preset, which always comes first and which the app never deletes, renames, colors, gives another icon, or moves. Presets keep a user-defined order, an optional color, one of a fixed eight-color palette or any custom color, and an icon from a curated set of 40. New presets are appended after the Default preset, without a color and with the layers icon. Reordering requires every current preset exactly once, keeps the Default preset first so no other preset can move above it, and renumbers positions densely after each organization change. Names are trimmed and unique under NFKC plus full Unicode case folding; a duplicate is refused with "Preset names must be unique." Presets, their memberships, and library folders are machine-local: they live in the database, never sync, and never make Sync report changes. Adding skills to a preset and removing them has no UI for now: the engine supports both, each idempotent, and Library has no selection.

Library folders group library skills for browsing only. A skill is in at most one folder, or in none; folders are separate from presets, and nothing applies them. While Library lists every skill, the header shows its folder tabs in place of the breadcrumb: All skills, a one-point divider, each folder in its stored order, then Add folder, a plus glyph with an "Add folder" tooltip, in one strip that scrolls sideways when it overflows. Tabs are small ghost buttons with 13-point labels: the chosen one shows the theme's muted fill, light gray in the light theme and dark gray in the dark theme, in the foreground color, while the others and the Add folder glyph use the muted text color until hovered. All skills is chosen at launch. Choosing a tab narrows the page to that folder's skills, together with search, and the skill count follows; a folder with no skills reads "No skills in <name>". The choice stays while other pages are open, is not part of Back and Forward, and falls back to All skills when the chosen folder is deleted. Preset pages and skill pages keep the breadcrumb, so folder and preset filters never combine. Add folder shows an inline name field in its place, a borderless input in the chosen tab's fill, and double-clicking a folder tab chooses it and edits its name the same way; Enter saves, while Escape, leaving the field, or an empty name cancels. A created folder's tab shows at once, after the other folders, while it is saved; a refused one disappears and its error is reported. A refused name, such as a duplicate, reports its error as preset names do. While another operation runs, Add folder is inactive and Enter leaves the field open with its name. Right-clicking a folder tab opens Rename and Delete…; Delete… asks "Delete <name>? Its N skills stay in the library." and leaves those skills unfiled. All skills has no menu. Folder tabs reorder by dragging exactly as presets do, sideways: the dragged tab lifts into a floating tab with a shadow that follows the pointer, which shows a closed hand until release, leaving its slot empty. Once the floating tab's leading edge passes the middle of a neighbouring tab and the gap after it, the tabs it passes slide 180 milliseconds aside to show the order a drop would save. Releasing the pointer anywhere saves that order, and the floating tab settles into its slot; releasing it on itself does not choose it. The new order is shown while it is saved, and a save that fails, or one refused while another operation runs, slides back to the stored order. Reduced motion moves tabs without sliding. All skills and Add folder do not move. New folders are appended last, and reordering requires every current folder exactly once. Folders have no color, icon, or count. Right-clicking a skill's row or card opens its menu with Move to folder, a submenu of None and each folder with a check on the current one; it is disabled while there are no folders or another operation runs. While All skills is chosen, a filed skill's dates line starts with the folder glyph and the folder's name. Folder names follow the preset name rules, with the refusal "Folder names must be unique.", and folders are renumbered densely after each organization change.

The page starts with a search field with a search glyph and a clear button, the Needs update filter (see Skill updates), and the number of listed skills, then, at the trailing edge, a GPUI Kit segmented control with List and Grid segments. Search matches the slug or description, ignoring case, and an empty result shows "No skills match '<query>'". Skills are listed alphabetically by slug, ignoring case. The chosen view is a machine-local preference, List by default, and survives restart. List shows one row per skill: the slug, one description line, its dates, and the skill's presence. Grid shows cards with the slug, two description lines, dates, and presence, in as many columns at least 260 points wide as fit. A drifted skill's row or card shows a warning-colored alert-circle glyph after its slug, with the tooltip "Changed outside SkillBinder" (see Records and drift). Clicking a row or card, outside its agent chips and their "+N" chip, or pressing Enter or Space while it has keyboard focus, opens the skill's page; rows and cards show the theme's secondary fill while hovered. Dates read "Imported 3 days ago · Modified 2 hours ago" in the largest whole unit, or "just now" under a minute, and each one's tooltip shows the exact local date and time. Imported is the import time the database records on this device; a skill that arrived through Pull has none and shows only Modified. Modified is when the newest file of the skill's managed copy last changed on this device, read from the file system each time the library is projected, so on another device it reflects that device's checkout.

Presence shows one chip per Agents row whose global skill directory held a copy with the skill's content at the last scan: Universal for the universal agents together, even when only one of them is detected, then each other detected agent in Agents section order. A copy counts when the scan found it in the global skill directory of one of the row's agents, directly or through a link, as on the agent page and in the sidebar counts. Workspace copies are not part of presence, so there are no workspace chips. Each chip is a small secondary tag holding the agent's avatar and its Agents section name. The avatar shows the agent's full-color logo on white when one is bundled, otherwise its monochrome logo or the square terminal glyph in the text color; Universal uses the layers glyph. A chip's tooltip shows the global skill directory, and Universal's adds a line "Used by <names>" naming its agents. Clicking a chip opens that agent's page or Universal's. Three chips show before the rest collapse into a "+N" chip whose tooltip names them. Before the first scan presence reads "Not scanned yet", and a library skill no detected agent holds reads "Not in any agent".

A skill's page shows the skill's `SKILL.md` as GPUI Kit Markdown with selectable text, and its leading YAML frontmatter as a key and value table. The file is read off the GPUI thread when the page opens. Leaving the page discards a read still in flight; the engine still finishes that read, which the preview limits bound. A `SKILL.md` that is binary, oversized, or unreadable shows the preview's explanation instead. An `http` or `https` link opens in the browser; other links, including relative links to the skill's other files, do nothing. Remote images do not load: the app has no HTTP client, so the skill page makes no network requests. The page is read-only.

Bounded file previews, used by skill pages, list at most 5,000 entries and depth 32; text is limited to 128 KiB. Binary and oversized files remain listed with an explanation. Relative-path and canonical containment checks reject traversal and escaping links.

## Skill updates

A library skill without a source learns one after each completed scan when a found copy's Git tree id equals the skill's recorded tree and a `skills` lock entry traces that copy, as importing it would; this covers skills imported before sources were kept and skills that arrived by Pull. Only the database learns the source then, so learning never dirties the library ahead of a Pull; the next Push or Sync that pulls nothing writes it into the skill's record, `records/<slug>.toml`, and commits it, and reconciling a record without a source keeps the learned one. Each lock file is read once per learning pass. A learned source is never removed when the copy goes away, and a copy whose content differs teaches nothing. A library skill with a source is checked for updates after each completed scan, so on launch, when the window regains focus, and after an import, an update, or a reinstall, at most once an hour for the same source and recorded tree, on a thread of its own. The check fetches each source repository and ref once, shallow and without blobs, into a cache under application data, takes the skill's folder from the fetched commit, and compares its Git tree id with the skill's recorded tree: an equal tree is up to date without fetching or writing a file, and only a different one is checked out into staging and inspected; the comparison is not with its library content, so a drifted skill has an update only when its source no longer holds its recorded content. Changed content that an update would refuse, because it is blocked, has invalid skill metadata ("The source's current version has invalid skill metadata."), or has no files, reads as a failed check with that reason instead of an update. A skill pinned to a commit is never checked. Checks use the same verified Git as Sync, with prompts disabled and user credential helpers available, a 120-second timeout per fetch, and the app-owned raw attributes in each cache; checks and updates keep separate caches. Results are kept in memory, apply only while the skill's source and recorded tree are unchanged, and are replaced by the next check after launch.

While a skill has an update, its List row ends in an Update button, its Grid card shows one beside its name, and its page header shows one; Library's header shows "Update all (N)" while N skills have an update, whatever folder tab or search is chosen. Preset pages have no Update all. Library and preset pages have a GPUI Kit segmented control with All and "Needs update N", where N counts the skills with an update among those that search, the preset, and the folder tab leave. Needs update lists only those skills. All is chosen at launch, and the filter returns to All, as search clears, when another route opens. Needs update with no skills reads "No skills need an update". Update and Update all apply at once, without review. Each skill updates on its own, and one removed meanwhile counts as failed: its source is fetched again, its folder is checked out and inspected, and content that is blocked, has invalid skill metadata, or has no files is refused, since an update cannot ask for the acknowledgement an import of invalid metadata needs. The skill's new record, the fetched tree with its source, is written by the same journal after the moves and before the database commit, so recovery finishes it with them, and rolling back restores the previous record. New content replaces the skill's directory through a journaled pair of moves, so recovery treats it like an import; when the library content already equals the fetched content, the journal has no moves and only writes the record and saves the drift. A source folder with more than 5,000 files and folders, counted from Git's tree objects before any file is fetched, is refused with "The source's folder has too many files to check.", and one holding a Git submodule with "The source's folder holds a Git submodule, which SkillBinder cannot check out.", since its content would check out as an empty folder. The skill keeps its slug, source, import time, folder, and presets, and the update remains uncommitted until Push or Sync. Afterwards the page shows "Updated N · M failed" until it changes. A skill page shows "Couldn't check for updates: <reason>" when its check failed, "Its source no longer has this skill." when the fetched commit has no folder at the source's path, and "Couldn't update: <reason>" after a failed update. Copies in agents' and workspaces' directories are never written; an older copy no longer counts toward presence, and Discovery treats it as in library.

## Records and drift

Every library skill has a record, `records/<slug>.toml` beside `skills/`, which syncs with it (ADR 0005). It holds `tree`, the 40-digit hexadecimal Git tree id of the content the skill should have, and an optional `[source]` table with the source's `url`, `ref`, and `path`. Importing, updating, and reinstalling write it; users never edit library skills. Reconciliation (see Synchronization) reads the record of each skill it inspects. A skill without a readable, valid record gets one from its current content, without a source. The database caches it at once, and its file is written into `records/` by the next Push or Sync that finds nothing to pull, which commits it; written earlier, it would dirty the library and block a Pull of what other devices pushed. Source learning also considers a found copy the library holds by slug, and a Lost skill that learns a source becomes Restorable. The database migration that added records forgets the reconciled commit, so every skill is rehashed once, and every open also rehashes the skills whose record is not cached yet, even in a library without a commit, so skills imported before records existed get theirs.

A skill has drifted when its inspected content's tree differs from its record's, such as after a Pull of content whose record did not change. It is Restorable when the library's Git objects hold the recorded tree or the record has a source, and otherwise Lost. Copies in agents and workspaces never make a skill drift. A drifted skill's page shows, in the warning color, "Changed outside SkillBinder. Reinstall restores the content its record holds." when it is Restorable, and "Changed outside SkillBinder. Neither the library's history nor the skill's source holds its recorded content any more, so it can't be reinstalled." when it is Lost. A Restorable skill's page header has a Reinstall button, before Update when both show. Reinstall restores the recorded tree from the library's own Git objects, checking it out through a scratch bare repository that borrows them through `objects/info/alternates`, so the library's index and working tree are untouched. Otherwise it fetches the source as an update does and uses its folder only when the folder's current tree equals the recorded one, and when neither holds it, Reinstall fails with "Neither the library's history nor the skill's source holds its recorded content." The skill is then marked Lost, so its page no longer offers Reinstall. Reinstall never moves a skill to newer content. Its replacement is one journal exactly like an update's, record included. A reinstall remains uncommitted until Push or Sync, and a scan runs after it. The skill's page then shows its restored content. Drift is only found when the library is reconciled, so an edit inside the library folder is noticed once Git reports it as changed, such as after a Pull.
